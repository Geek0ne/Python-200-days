🔍 查漏补缺：常见知识盲区

盲区 1：装饰器 vs 闭包

python
# 闭包 = 函数 + 捕获的变量
def outer(x):
    def inner(y):
        return x + y
    return inner

# 装饰器 = 闭包的特殊应用（接收函数，返回函数）
def decorator(func):
    def wrapper(*args, **kwargs):
        print(f"调用 {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

盲区 2：生成器 vs 迭代器

python
# 迭代器：实现了 __iter__() + __next__() 的对象
# 生成器：用 yield 语法创建的迭代器（更简洁）

# 迭代器
class Count:
    def __init__(self, n):
        self.n = n
        self.current = 0
    def __iter__(self):
        return self
    def __next__(self):
        if self.current >= self.n:
            raise StopIteration
        self.current += 1
        return self.current

# 生成器（等价写法）
def count(n):
    for i in range(1, n + 1):
        yield i

盲区 3：深拷贝 vs 浅拷贝

python
import copy

a = [[1, 2], [3, 4]]

b = a              # 引用（同一个对象）
c = copy.copy(a)   # 浅拷贝（外层独立，内层共享）
d = copy.deepcopy(a)  # 深拷贝（完全独立）

a[0][0] = 999
# a → [[999, 2], [3, 4]]
# b → [[999, 2], [3, 4]]  (跟着变)
# c → [[999, 2], [3, 4]]  (内层共享，也变了！)
# d → [[1, 2], [3, 4]]    (完全独立)

盲区 4：多线程 vs 多进程 vs asyncio

python
# GIL 限制：CPU 密集型 → 多进程；IO 密集型 → 多线程/asyncio

# 多线程（IO 密集型）
import threading
t = threading.Thread(target=io_task)
t.start()

# 多进程（CPU 密集型）
from multiprocessing import Process
p = Process(target=cpu_task)
p.start()

# asyncio（IO 密集型，单线程）
async def io_task():
    await asyncio.sleep(1)

盲区 5：dataclass vs 普通类

python
from dataclasses import dataclass

# 普通类（需要写很多样板代码）
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y
    def __repr__(self):
        return f"Point(x={self.x}, y={self.y})"

# dataclass（自动生成 __init__, __repr__, __eq__ 等）
@dataclass
class Point:
    x: float
    y: float

💡 思考题

  1. 知识连接：装饰器、闭包、上下文管理器之间有什么关系？它们的共同底层机制是什么？

参考答案

三者是「层层递进」的关系，共同的底层机制是函数是一等对象 + 闭包（捕获外部变量的函数）+ 协议（约定好的特殊方法）。

  • 闭包是地基：内层函数记住并持续访问外层函数的变量，即使外层已返回。def outer(x): def inner(y): return x+y; return inner 里，inner 就「背着」x 走。
  • 装饰器是闭包的应用：它接收一个函数、返回一个闭包 wrapper，wrapper 捕获原函数 func，调用时先加增强逻辑再委托 func。本质就是 f = decorator(f)。
  • 上下文管理器是协议的应用：对象实现 __enter__/__exit__，with 语句保证进入时调用前者、离开时（无论是否异常）调用后者。用 @contextmanager 装饰生成器时，底层又是闭包 + 生成器把 yield 前后拆成 enter/exit。

一句话串起来：闭包提供「携带状态的能力」，装饰器用它包装函数，上下文管理器用协议包装一段作用域。它们都体现了 Python「用对象和协议表达控制流」的设计哲学。

  1. 设计决策：如果要设计一个聊天系统，你会选择多线程、多进程还是 asyncio？为什么？

参考答案

选 asyncio。聊天系统是典型的 I/O 密集型 + 高并发连接场景：成千上万条连接大部分时间在「等消息」，真正计算极少。

  • asyncio：单线程事件循环，一条连接等待时立刻切去服务别的连接，轻松扛住上万并发（C10K），内存开销小（协程比线程轻得多），没有线程锁的心智负担。这正是 WebSocket 聊天室的标准做法。
  • 多线程：每条连接一个线程的话，上万线程会吃光内存、上下文切换开销巨大；且 GIL 让 CPU 计算无法并行，对聊天这种少计算的场景没收益。
  • 多进程：进程更重，适合 CPU 密集任务；聊天系统用它是杀鸡用牛刀，还要处理跨进程的消息广播，复杂度陡增。

补充：若聊天里有重计算（如消息内容审核模型），把那部分丢进进程池/线程池，主循环仍用 asyncio——「asyncio 管连接，池子管计算」是常见组合。

  1. 性能意识：在什么场景下，生成器比列表更合适？举出 3 个具体例子。

参考答案

核心判断：数据量大、或只需逐个消费、或可能提前终止时，生成器（惰性求值，一次只算一个）比列表（一次性全算出来存内存）更合适。三个例子：

  • 读大文件：for line in open('10GB.log') 逐行产出，内存恒定几 KB；若 readlines() 成列表，10GB 直接撑爆内存。
  • 无限/超长序列：斐波那契数列、传感器实时数据流这种「没有尽头」的序列，只能用生成器 yield，列表根本无法装下无限元素。
  • 流水线处理 + 提前退出：next(x for x in huge_data if valid(x)) 找到第一个合格项就停，后面的元素压根不计算；列表推导式则会先把全部元素算完，浪费大量时间和内存。

共同点：生成器把「计算」推迟到「真正需要那一刻」，省内存也省无用功。

  1. 代码质量：SOLID 原则中，你认为哪条最难遵循？为什么？

参考答案

（开放题，以下为参考观点）我认为开闭原则（OCP：对扩展开放、对修改关闭）最难。

原因：它要求「加新功能时不改旧代码」，但现实中需求往往直接冲击已有逻辑。比如给支付系统加一种新支付方式，理想做法是新增一个 PaymentStrategy 类而不碰旧代码；可如果最初没预留抽象接口，就得回头重构一大片——OCP 难在「提前设计」与「避免过度设计」之间的平衡：抽象留少了，扩展时要改旧代码；留多了，又变成 YAGNI（用不到的过度设计）。

它难的本质是：其他原则（如单一职责）主要约束「当下怎么写」，而 OCP 约束的是「未来怎么变」，需要对领域变化方向有预判，这恰恰是最难的部分。实践上靠「识别真正会变的轴（如支付方式、导出格式）再抽象」来逼近，而不是处处预留接口。
