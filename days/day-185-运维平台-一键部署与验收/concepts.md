# Day 185 概念与原理 —— 一键部署与端到端验收

> 这一课的主题不是"写个脚本把程序跑起来"，而是**让"部署成功"变成一个程序能判定的结论**。
> 所有代码在 `code/` 下，全部标准库、可离线自证、真机跑过。

---

## 1. 一键部署到底是什么

一句话：**把一次发布里所有"可能做错、做慢了会出事故"的动作，变成一条有预检、有探针、有回滚的流水线。**

不是这些：
- ❌ 不是"少敲几条命令"（省下的那点时间不值钱）
- ❌ 不是"把所有命令塞进一个 shell 脚本"（那是把事故打包）
- ❌ 不是"部署成功就是退出码 0"（如果没人验证业务真的能用，0 就是假的）

是这些：
| 环节 | 要回答的问题 | 本课实现 |
|---|---|---|
| 预检 | 现在能不能安全地动线上？ | `preflight()`：端口占用的**身份**、目录可写、目标文件存在 |
| 启动 | 进程起来了吗？**能干活了吗？** | 存活探针 + 就绪探针（两个都要） |
| 验收 | 业务真的能用吗？ | `03-smoke-acceptance.py`：9 项断言，含真实数据条数比对 |
| 回滚 | 坏了能不能自己退回去？ | 就绪/验收失败 → 停新版 → 起旧版 → 再验收 |
| 记录 | 现在线上是哪个版本？ | `current.json` + 追加式 `history.jsonl` |

## 2. 可判定性：退出码就是一线的接口

脚本要给"机器"用（CI、告警、发布平台），所以退出码必须是**语义明确且稳定**的：

```text
0  成功
3  预检失败（什么都没改，可以安全重试）
4  新版未通过验收，但已回滚（线上是好的，需要人看为什么新版不行）
5  回滚也失败（真正的事故，必须立刻叫人）
1  脚本自身出错（参数错误、断言失败）
```

为什么要把 3/4/5 分开：告警的动作不一样。
3 可以自动重试；4 要去看新版日志；5 要立刻停止一切自动操作并拉人。
合并成一个"非 0"就丢掉了这些信息。

## 3. 存活（liveness）≠ 就绪（readiness）

这是部署里最容易被合并、也最容易因此出事的两个概念。

| 探针 | 回答的问题 | 失败的后果 | 谁用 |
|---|---|---|---|
| liveness | "进程/容器还活着吗？" | 重启它（K8s 会杀容器） | 看门狗、K8s livenessProbe |
| readiness | "现在能安全地接流量吗？" | 从负载均衡里摘掉，**不重启** | K8s readinessProbe、部署脚本 |
| startup | "启动完了吗？" | 在启动期间豁免其他探针 | 慢启动应用 |

本课的服务 `00-platform-api.py` 用真实行为演示了这一点：
`/healthz` 在进程刚起来时就 200，而 `/readyz` 在 warmup（加载数据/建连接池）完成前必须 **503**。

反例（很多项目真的这么写）：
```python
# 只检查端口能不能连上，然后就开始导流量
if port_open(port): print("deployed!")
```
端口 listen 是**内核**行为，业务可用是**应用**行为，中间隔着 warmup。
只用一个探针的系统，会在"发布后第一秒"出现一批 5xx —— 而且因为太快，你往往归咎于"流量突增"。

## 4. 进程身份：PID 不是凭证，`cmdline` 才是

一个部署脚本要能回答："这个 PID 到底是不是我的服务？" 三个真实陷阱：

**陷阱 1：陈旧 PID 文件。** 服务被 `kill -9`（或机器重启）后，`app.pid` 还在。
于是脚本认为"它在跑" → 跳过启动 → **线上其实一直没起来，CI 却是绿的**。

**陷阱 2：PID 复用。** 进程号会被系统回收再分配。那个号现在可能是 cron、sshd、数据库。
照着化石 `kill` 一下，你**静默地**杀掉了无关进程。04 号示例里这个动作真机跑过：
一个 `sleep 120` 被 `naive_stop()` 直接杀掉，且不留任何错误。

**陷阱 3：僵尸进程不是活进程。**
子进程退出后如果父进程没 `wait()`，它会变成僵尸（state=`Z`）。
关键点：**僵尸的 `/proc/<pid>` 目录依然存在**，所以
"用 `os.path.exists('/proc/<pid>')` 判断进程活着"是错的 —— 会永远为真。
正确判据：读 `/proc/<pid>/stat`，取状态字符，`Z/X` 视为已死。

正确姿势（01 号示例的 `validate_pid`）：
```python
ok, pid, why = validate_pid(pidfile, marker="/path/to/our/service.py")
# 1) pidfile 存在  2) pid 数值合法  3) 进程真的活着（非僵尸）
# 4) /proc/<pid>/cmdline 里必须出现 marker —— 这一条才是"身份"
```

为什么 `cmdline` 能做凭证：它由内核维护，进程自己改不了（改 argv 也只能改自己内存里的副本，
`/proc` 里读到的仍是启动时的内容）。**"这个号属于谁"必须问内核，不能问一个文本文件。**

## 5. 优雅停机：SIGTERM 的真正含义

信号语义（部署脚本必须知道的三个）：

| 信号 | 语义 | 谁该处理 |
|---|---|---|
| SIGTERM | "请你收拾一下再走" —— 可以捕获、可以拖延 | 应用：停止接新请求 → 排空在途 → 退出 |
| SIGINT | 同 SIGTERM（Ctrl-C） | 同上 |
| SIGKILL | "立刻死" —— 不可捕获、内核直接回收 | 没人能处理，所以只能作为**最后手段** |

**"我注册了 SIGTERM handler" ≠ "在途请求会被做完"**，这是本课最重要的实测结论：

- 第一版实现只做了 `signal.signal(SIGTERM, on_term)` + `httpd.shutdown()`，
  实测结果：SIGTERM 后进程 **0.297s** 就退出了，正在处理的 `/slow?ms=1500` 请求
  被连根切断，客户端拿到 `RemoteDisconnected`。
- 根因：`socketserver.ThreadingMixIn` 的处理线程是 daemon 线程，
  `server_close()` 不会为它们阻塞；主线程一返回，解释器就把 daemon 线程带走。
- 修复：**自己记账**。维护在途请求计数器 + Condition，停机时
  `shutdown()`（停止接收）→ `wait_idle(宽限期)`（排空）→ `server_close()`（收尾）。
- 复测：同一请求 **200**，耗时 1.202s（完整跑完 1200ms），进程随后 **0.051s** 退出；
  服务日志出现 `{"msg":"drained","waited_s":0.839,"max_concurrent":1}`。

排空还要有**宽限期**（本课默认 10s）：无限等 = 停机卡死，滚动发布会永远卡在最后一步。
宽限期用完就要记一条日志（`drain_timeout`）—— 这本身是一个应该告警的事件。
