# Day 186 · 概念与原理：资产测绘与子域名收集

> 本文件是 Day 186 的"概念手册"，README.md 是"课堂 + 实验记录"。
> 所有结论都服务于一个目标：**把互联网上属于某个组织的名字，变成一份可差分、可查询的资产清单。**

---

## 1. 为什么从"域名"开始

安全工作的第一步不是扫漏洞，而是回答"我到底有哪些东西"。

一个组织的暴露面通常长这样：

```text
根域名 example.com
  ├── www.example.com        → 官网（CDN）
  ├── api.example.com        → 业务 API
  ├── dev.example.com        → 开发环境（常常忘记下线）
  ├── vpn.example.com        → 远程入口
  └── *.internal.example.com → 泛解析，可能是测试环境
```

**为什么域名是第一等公民：**
- 它是**唯一稳定的入口标识**。IP 会变（CDN、云主机），域名相对稳定。
- 证书、DNS、HTTP、邮件都围绕域名组织，后续所有探测都能挂在域名下。
- 攻击者也是这么找目标的：先枚举名字，再解析，再扫端口。

**资产模型的五层**（本项目的骨架）：

| 层 | 数据 | 回答的问题 | 本日/后续 |
|---|---|---|---|
| L1 域名 | example.com | 从哪找起 | Day 186 |
| L2 子域名 | api.example.com | 还有哪些入口 | Day 186 |
| L3 IP | 192.0.2.10 | 实际落在哪台机器 | Day 186 |
| L4 端口/服务 | 443/https, 22/ssh | 开了什么 | Day 187 |
| L5 漏洞 | SQLi, XSS | 有什么问题 | Day 188 |

## 2. DNS 速查：枚举到底在查什么

### 2.1 记录类型

| 类型 | 含义 | 枚举时的用途 |
|---|---|---|
| `A` | 域名 → IPv4 | 判断主机是否存在 |
| `AAAA` | 域名 → IPv6 | 同上，且常被忽略 |
| `CNAME` | 别名 → 另一个域名 | 识别 CDN/SaaS，追真实源站 |
| `NS` | 该域的权威服务器 | 找 DNS 服务商、做区域传送测试 |
| `MX` | 邮件服务器 | 发现邮件资产、SPF 配置 |
| `TXT` | 任意文本 | SPF/DKIM/域名验证，泄露第三方服务 |
| `SOA` | 区域起始授权 | 区域信息、管理员邮箱 |

### 2.2 一次解析发生了什么

```text
应用 getaddrinfo("api.example.com")
   │
   ├─ 1. 查 /etc/hosts、nsswitch 配置
   ├─ 2. 查本地缓存（systemd-resolved / nscd）
   ├─ 3. 问递归解析器（如 8.8.8.8）
   │      └─ 递归解析器可能也有缓存（TTL 内直接返回）
   ├─ 4. 递归解析器从根 → .com → example.com 的权威 NS 逐级问
   └─ 5. 返回 A/AAAA，应用拿到 sockaddr
```

**为什么要懂这条链：**
- **缓存会污染性能测试**。第二次解析同一域名往往 <1ms，测出来的"加速比"是假的（本日实验 B 就踩了）。
- **本地 hosts 会骗人**。测试环境把域名指到 127.0.0.1 时，枚举器会"发现"一个假资产。
- **递归解析器可能做 NXDOMAIN 缓存**，刚上线的子域名短时间内查不到。

### 2.3 常见返回码

| 现象 | 含义 | 枚举器该怎么处理 |
|---|---|---|
| 有 A/AAAA | 主机存在 | 记入资产 |
| `NXDOMAIN` | 名字不存在 | 忽略 |
| `SERVFAIL` | 解析器/权威服务器故障 | 记录 error，别当成"不存在" |
| 超时 | 网络丢包或限速 | 重试一次，仍失败则标记 unknown |
| 泛解析命中 | 任意名字都有 IP | 先探测 wildcard，再过滤 |

## 3. 子域名枚举的三条路线

### 3.1 字典爆破（主动）

把 `www/api/dev/...` 拼到根域名后面逐个解析。

- **优点**：可控、可复现、能发现未上证书的内网风格名字。
- **缺点**：字典覆盖率决定结果；会产生大量 DNS 查询（可能触发限速）；对目标"可见"。
- **关键指标**：候选数、命中率、每秒查询数（QPS）、错误率。

**为什么要并发**：每次解析是网络 I/O，串行 200 个词 × 20ms = 4 秒；16 线程可压到 0.27 秒（本日实测）。

### 3.2 证书透明日志（被动）

CA 签发证书时必须公示到 CT 日志。查询 `crt.sh` 的 JSON 接口，就能拿到历史上出现过的全部主机名。

- **优点**：不碰目标、能发现字典里没有的名字（如 `blog-stage`、`pycon-archives`）。
- **缺点**：只能看到"签过证书"的名字；接口不稳定（本日第一次 502，重试后成功）；数据可能滞后。
- **必须清洗**：换行拆分、`*.` 前缀、大小写、末尾点、后缀伪装（`evil-example.com` 不是 `example.com` 的子域）、邮箱条目。

### 3.3 被动 DNS（补充）

商业/公开的 Passive DNS 数据库记录"谁在什么时候解析过什么"。

- **优点**：能看到历史解析、已下线资产。
- **缺点**：多数要付费；数据质量和覆盖差异大。
- **课程内不依赖**：接口通常需要 key，不适合作为可复现实验。

### 3.4 三条路线怎么选

```text
要快、要全、能接受噪音        → 字典 + CT 合并
不能碰目标（红队初期/合规）   → CT + 被动 DNS
要找内网命名规律              → 字典（配合泛解析检测）
```

## 4. 泛解析（Wildcard DNS）：枚举器最大的假阳性来源

配置长这样：

```text
*.example.com.  300  IN  A  192.0.2.99
```

效果：**任何** `随便什么.example.com` 都能解析到 `192.0.2.99`。

如果枚举器不做处理，1 万个字典词会得到 1 万个"资产"，全部指向同一个 IP。后续端口扫描会把同一个 IP 扫一万遍。

**检测方法**（本日代码实现）：
1. 生成 3 个随机标签（如 `x7f2k9q1.example.com`）
2. 解析它们，收集 IP 集合
3. 枚举时，若某主机的 IP 集合**完全等于**泛解析集合 → 判定为假阳性并丢弃

**为什么取 3 次**：泛解析可能轮询返回一组 IP，单次采样不全。

**注意**：如果真实子域名恰好也解析到那组泛解析 IP，会被误杀。更严谨的做法是结合 HTTP 响应差异、证书 SAN 等二次确认。

## 5. 快照与差分：资产清单的价值在"变化"

单次扫描 = 一张照片。安全运维要的是"昨天和今天有什么不同"。

### 5.1 数据模型

```sql
snapshots(id, label, taken_at)
assets(snapshot_id, host, ips, source)
```

- 每次扫描写一个 `snapshot`，资产行挂在快照下。
- **不要覆盖式更新**：覆盖会丢掉历史，无法回答"这个 dev 域名是什么时候出现的"。
- `ips` 存 JSON 数组字符串，比较时解析后比集合，避免顺序导致的假变化。

### 5.2 差分口径

| 类别 | 定义 | 安全含义 |
|---|---|---|
| added | 本次有、上次无 | 新上线/新暴露，重点看 |
| removed | 上次有、本次无 | 下线/解析失败，可能是事故 |
| changed | 两边都有，IP 不同 | CDN 切换正常；指向新 IP 要查 |

### 5.3 本日踩到的真坑：不同来源不能直接差分

第一次实验用"CT 快照（74 个名字，无 IP）"对比"DNS 快照（8 个有 IP）"，结果报 **67 个消失**。

这不是资产消失，而是**口径不同**：
- CT 只证明"这个名字签过证书"，不代表现在能解析；
- DNS 只查了 20 个字典词，覆盖不了 CT 的 74 个名字。

**正确做法**：先把多来源合并成同一口径的快照（名字集合 ∪ 解析结果），再和历史同口径快照比。
本日第三次快照 `merged` 就是这么做的，差分结果才可信。

## 6. 并发模型：为什么线程池而不是多进程

- DNS 查询是 **I/O 密集**：线程在 `getaddrinfo` 等待时会释放 GIL。
- `ThreadPoolExecutor` 开销小、共享内存方便汇总结果。
- 进程池适合 CPU 密集（如大规模正则匹配），不适合这种"等网络"的任务。

**参数经验**：
- workers 太小 → 等待时间叠加；太大 → 本地文件描述符/解析器限速/目标 DNS 限速。
- 先用 16~32，观察错误率和 QPS；出现大量 timeout 就降。
- 生产环境要加**令牌桶限速**和**每域名并发上限**，避免被当成 DNS 放大攻击。

## 7. 合规与边界（必须写进代码注释）

- 只对**你拥有或获得书面授权**的域名做枚举。
- 子域名枚举只发 DNS 查询，影响低，但仍可能触发对方 SOC 告警。
- 不要对第三方域名做高频爆破；不要使用开放解析器做反射攻击。
- CT 日志是公开数据，查询它不接触目标，但**使用结果攻击目标仍然是另一回事**。

## 8. API 速查

| 需求 | 标准库/接口 | 关键参数 | 备注 |
|---|---|---|---|
| 解析主机 | `socket.getaddrinfo(host, None)` | `family`, `type` | 返回 sockaddr 列表，含 IPv4/IPv6 |
| 仅 IPv4 | `socket.gethostbyname_ex(host)` | — | 不返回 IPv6 |
| 设置超时 | `socket.setdefaulttimeout(s)` | 全局 | 更推荐外层超时控制 |
| 并发 | `concurrent.futures.ThreadPoolExecutor` | `max_workers` | I/O 密集首选 |
| HTTP GET | `urllib.request.urlopen(req, timeout=)` | `headers` | 记得设 User-Agent |
| JSON | `json.loads/dump` | `ensure_ascii=False` | 中文可读 |
| SQLite | `sqlite3.connect` + `executemany` | `with conn:` 事务 | 批量写入必须用事务 |

## 10. 深入：getaddrinfo 背后的真实行为

`socket.getaddrinfo` 不是一个"纯 DNS 函数"，它是 **NSS（Name Service Switch）** 的统一入口：

```text
getaddrinfo(host, port, hints)
   ├─ /etc/nsswitch.conf: hosts: files dns
   ├─ files  → /etc/hosts（本地覆盖，测试环境常用）
   ├─ dns    → 读取 /etc/resolv.conf 的 nameserver
   └─ 返回 addrinfo 链表（可能同时含 IPv4/IPv6/多条 A 记录）
```

**三个容易踩的点：**

1. **超时不是参数**。`getaddrinfo` 没有 `timeout` 参数，只能靠
   `socket.setdefaulttimeout()` 或信号/子进程兜底。生产级枚举器通常自己实现
   DNS 报文（`dnspython`）以便精确控制重试与超时。
2. **返回值可能重复**。同一 IP 因 `AI_ADDRCONFIG`、多网卡、CNAME 链出现多次，
   必须 `set()` 去重再排序，否则差分时顺序变化会被误判成"IP 变化"。
3. **错误类型不统一**。`gaierror`（名字不存在）、`timeout`、`OSError` 都可能出现；
   把异常一律当成"不存在"会掩盖解析器故障，必须单独计数。

**为什么不直接 `gethostbyname`：** 它只返回 IPv4 且是线程不安全的历史接口
（CPython 内部有锁），在高并发下会变成串行瓶颈。

## 11. 证书透明日志的数据结构

crt.sh 返回的是一个 JSON 数组，每条记录大致包含：

| 字段 | 含义 | 清洗要点 |
|---|---|---|
| `name_value` | 证书覆盖的名字，多行 | 按换行拆开，逐条归一化 |
| `common_name` | 主 CN | 可能为空，作为兜底 |
| `issuer_name` | 签发 CA | 可用来识别自签/测试证书 |
| `not_before/not_after` | 有效期 | 过期证书的主机可能已下线 |
| `entry_timestamp` | 入日志时间 | 判断"新出现"的时间线 |

**为什么 4,013 条记录只剩 74 个名字：**
- 同一主机每年续签多次 → 大量重复；
- 一张证书含多个 SAN → `name_value` 一行多个名字；
- 通配符 `*.example.com` 与具体名字重复；
- 还存在 `example.com` 根域、邮箱条目、大小写差异。

所以"记录数"≠"资产数"，报告里必须区分这两个指标，否则会虚报规模。
