# Day 184 概念与原理 —— 日志收集 + 可视化

> 今天不是"用某个日志框架"，而是**把日志从「人读的文本」变成「能查的数据」**。
> 这一章先把概念和原理讲透，代码示例（`code/` 目录）是这些原理的可运行证明。

---

## 1. 为什么需要「收集」：三个真实痛点

| 痛点 | 具体表现 | 今天的解法 |
|---|---|---|
| 日志散在各处 | 10 台机器 10 个文件，出事时挨个 ssh `grep` | 统一接收端（`02-log-ingest-server.py`） |
| 日志是给人看的 | `ERROR 用户支付失败 order=123` —— 想问"错误率多少"只能正则 | 结构化字段（`01-structured-logging.py`） |
| 日志会丢 | 轮转之后采集器还在读被 rename 的旧文件 | 抗轮转采集器（`03-log-collector.py`） |

三者是**一条管道上的三步**，少任何一步，"可视化"都是假的：
图上没数据的时候，你分不清是"真的没请求"还是"日志丢了"。

## 2. 日志的三种形态

1. **人读形态**：`2026-10-17 14:01:00 [INFO] 处理完成 order=123 耗时=12ms`
   - 优点：`tail -f` 就能看懂。
   - 缺点：机器解析要靠不稳定的正则（格式一变就全崩）。
2. **半结构形态**：`ts=2026-10-17T14:01:00+08:00 level=INFO order=123 duration_ms=12`
   - key=value，`grep` / `awk` 友好，解析比自然语言稳。
   - 缺点：值里带空格或引号就要转义，嵌套结构表达不了。
3. **结构化形态（JSON Lines）**：一行一个 JSON 对象
   ```json
   {"ts":"2026-10-17T14:01:00.123+08:00","level":"INFO","service":"api","request_id":"req-8f21","msg":"request handled","status":200,"duration_ms":12.4}
   ```
   - 天然可嵌套（`extra={"db":{"host":"...","rows":3}}`）。
   - **每行一个对象**是关键：它能被按行增量读取（`tail -f` / 采集器），
     而"整个数组一个大 JSON"做不到增量读 —— 必须读完才能解析。

> 设计原理：日志的第一消费者其实**是机器**（采集器、聚合器、告警器），
> 人是第二消费者。让机器省事的格式，最终也让人省事（`jq .duration_ms` 就完事）。

---

## 3. 结构化日志的字段设计

最小可用集（少一个都会在某个场景里卡住）：

| 字段 | 为什么必须有 | 没有会怎样 |
|---|---|---|
| `ts` | 事件发生时间，**必须带时区偏移** | 跨机房聚合时顺序错乱、桶对不上 |
| `level` | 过滤与告警的第一维 | 只能全量扫 |
| `service` | 多服务区分 | 混在一起分不清谁在报错 |
| `request_id` / `trace_id` | 串起一次请求的所有日志 | 只能靠时间猜，并发下必错 |
| `duration_ms` | 延迟分布（P50/P95/P99） | 无法回答"慢不慢" |
| `status` | 错误率分母/分子 | 无法算成功率 |
| `msg` | 人读的兜底短描述 | 看日志还得反查代码 |

两条实现上的硬规则（Python `logging`）：

- `extra={}` 的 key **不能和 LogRecord 自带属性重名**，否则 `KeyError`：
  撞名的坑包括 `msg`、`args`、`name`、`levelname`、`module`、`filename`、`exc_info`。
  示例里用 `logging.LogRecord("",0,"",0,"",(),None).__dict__` 取出全部保留名做白名单过滤。
- `exc_info=True` 的 traceback 要放在**独立字段**（如 `traceback`）而不是拼进 `msg`：
  这样"按错误类型聚合"就是 `GROUP BY error_type`，而不是正则。

## 4. 日志管道的四个阶段

```mermaid
flowchart LR
    A["应用<br/>结构化日志"] -->|write 追加| B["日志文件<br/>app.log"]
    B -->|"采集器跟随<br/>(inode, offset)"| C["采集器<br/>批量 + 重试"]
    C -->|"HTTP POST<br/>NDJSON"| D["接收端<br/>校验/入库"]
    D --> E[("SQLite WAL<br/>logs 表")]
    E -->|"GROUP BY 分桶"| F["看板 / HTML 报告"]
    C -.->|"投递失败"| G["spill 文件<br/>（降级不丢）"]
    E -->|"按级别/消息聚合"| H["告警规则"]
```

每一段都有它自己的失败模式，这才是"日志系统难"的真实原因：

| 阶段 | 典型失败 | 本项目里的对策 |
|---|---|---|
| 产生 | 格式不统一、时间没时区 | 统一 JSON Lines + 强制 ISO8601 |
| 采集 | 轮转/截断/半行导致丢或碎 | 监控 `(ino, size, mtime_ns)` 的状态机 |
| 传输 | 接收端重启、网络抖动 | 批量 + 指数退避重试 + 降级落盘 |
| 存储 | 并发写锁冲突丢日志 | WAL + `busy_timeout` + 批提交 |
| 查询 | 全表扫、把行拉进 Python 聚合 | 索引 + 在 SQL 里分桶 |

## 5. 采集的本质：一个「读文件 + 记位置」的状态机

采集器看着像 `tail -f`，其实是一个状态机，状态是三元组：

```text
(state) = (inode, offset, buffer)
```

- **为什么要 inode 而不是文件名**：`open("app.log")` 拿到的是那个时刻文件名指向的 inode。
  `logrotate` 默认用 `rename`：`app.log → app.log.1`，然后应用重新创建 `app.log`。
  采集器的 fd 还绑在旧 inode 上 —— 旧 inode 不再增长，新文件它根本不知道，
  **一条不报错地永久丢失**（这就是本日翻车实验）。
- **为什么要有 offset**：重启采集器时不能从头重读（会重复），也不能只记行号
  （半行会让行号错位）。字节偏移 + 只在换行处推进，是最稳的记法。
- **为什么要有 buffer**：应用写日志不是原子的。`write()` 两次调用之间，
  采集器可能正好读到一半 —— 此时 `json.loads` 必失败。只处理"以 `\n` 结尾"的完整行，
  尾巴留在 buffer 里等下一轮，是唯一正确的做法。
- **mtime 也是状态的一部分**：只比 `size` 会漏掉"truncate 后正好写成同样字节数"的情况
  （本日自证脚本抓到的真实 bug），所以判断截断要 `size < offset` **或** (`size <= offset` 且 `mtime` 变了)。

> 三种轮转语义都要认识：`rename`（新文件新 inode）、`copytruncate`（同 inode 大小归零）、
> `create`（先删再建）。前两种本项目都处理了，第三种等价于 `rename` 的检测路径。

## 6. 存储选型：为什么这一课用 SQLite

| 方案 | 单机可行性 | 适用规模 | 本课选择理由 |
|---|---|---|---|
| 纯文件 + grep | 有 | 极低 | 无法分桶聚合、无法多服务 |
| SQLite（WAL） | ✓ 零依赖 | 单机 10⁴~10⁶ 行/天 | 标准库自带，能在任何机器上复现实验 |
| Loki / ELK | 要起容器/集群 | 10⁷+ 行/天 | 本机跑不动 4GB 内存的 ES，读者也未必有环境 |
| ClickHouse | 要装 | 10⁹+ | 同上，属于"知道有这条路" |

选型批判视角：SQLite 的短板是**写入并发**（同一时刻只能一个写者）和**没有分布式**。
本课把它用到极限，然后明确告诉你什么时候该换成 Loki —— 这比"上来就集群"学到的东西多。

## 7. SQLite 的并发模型：两种 journal 模式与锁

SQLite 的锁是**库级**的，粒度比 MySQL/Postgres 粗得多。两种日志模式决定并发行为：

```text
① rollback journal（默认 delete 模式）
   写事务：   [SHARED] → [RESERVED] → [EXCLUSIVE] → 写主库 → 删 journal
   关键：拿到 RESERVED 后，别人还能读；一旦进入 EXCLUSIVE 落盘，**别人连读都不行**。
   所以"读多写少"也会被写卡住。

② WAL（write-ahead log）
   写事务：追加到 -wal 文件，读者继续读主库 + 自己的快照。
   关键：**一写多读不互斥**；写者之间仍然互斥（必须排队）。
   代价：多出 .db-wal / .db-shm 两个文件；备份要一起拷；网络文件系统上不要用。
```

**SQLITE_BUSY 是"立刻返回"的错误，不是"自动等"**。让写者排队要显式给：

```python
conn = sqlite3.connect(db, timeout=5.0)   # 等价于 connect 后的忙等待上限
conn.execute("PRAGMA busy_timeout=5000")  # 毫秒，覆盖上面的 timeout
```

两个反直觉点：

1. `timeout=0`（或 `busy_timeout=0`）不是"不等待"的优化，而是**关掉容错**：
   一撞锁就抛 `OperationalError: database is locked`。04 号示例里实测到的就是这个。
2. 读到一半要升级成写锁时会拿到 `SQLITE_BUSY_SNAPSHOT`，忙等待**救不了**，
   因为事务已经读过数据、状态不可回滚。对策是**一开始就用 `BEGIN IMMEDIATE`** 拿写锁
   （本项目的写入路径全部用 IMMEDIATE）。

## 8. 性能的三个杠杆

1. **提交次数**（最大杠杆）
   每条一次 `COMMIT` ≈ 每条一次 fsync。批提交把它降到 `N/batch` 次。
   实测（05 号示例）：逐条提交 → 批 1000 条一事务，吞吐差**一到两个数量级**。
2. **journal 模式**
   WAL + `synchronous=NORMAL` 比默认 delete + FULL 快一截。
   代价：断电时**可能丢最后几个已提交事务**（不是丢库，是不丢一致性但丢最新几条）。
   日志场景能接受这个取舍 —— 这是明确的设计选择，不是"忘了设 FULL"。
3. **索引是双刃剑**
   本课建了 `ts` / `(level, ts)` / `received_at` 三个索引：查询快，
   但每次写入要更新三个索引。日志表若纯追加、只按时间范围查，
   索引应精简到"查询真的用到的那几个"。

**可观测性的自我要求**：留一个"丢了没有"的度量。
采集器记 `lines_sent` / `lines_spilled` / `failed_batches`，
接收端记 `accepted`。三者对不上，就说明管道有问题 —— 这是日志系统的自证。

## 9. 可视化：从数据到决策

可视化的输入永远是**聚合结果**，不是原始行：

- 分桶时间序列：`GROUP BY CAST(strftime('%s', received_at) AS INTEGER)/60`
  → 得到"每分钟多少条"，才能画柱状/sparkline。
  （把时间存成可排序的 ISO8601 字符串，SQLite 的 `strftime` 能直接吃，不必存 epoch 整数。）
- 按级别分布：反映"健康度"，ERROR 占比是最常用的 SLO 指标。
- TOP 消息：反映"什么在刷屏"，通常能直接指出一个坏掉的循环或重试风暴。

两个受众两种渲染（06 号示例）：

| 受众 | 形态 | 为什么 |
|---|---|---|
| 值班工程师 | ASCII 看板（ssh 里能看） | 不需要浏览器、不需要开放端口、断网也能看 |
| 汇报/存档 | 单文件 HTML（内联 CSS，无 CDN/JS） | 邮件附件能打开，离线；比截图可查 |

**为什么不在报告里加 JS 图表库**：日志报告常被当附件转发到内网环境，
外部 CDN 会被墙或触发告警；纯粹为了好看而引入运行时依赖，是运维工具的反模式。

## 10. 常见误区清单（自查）

- [ ] 只比 `st_size` 判断轮转 → 漏掉 `copytruncate` 与同字节重写（本日真实 bug）
- [ ] 用 `readline()` 读正在被写的文件 → 半行被当成完整行，JSON 解析失败
- [ ] 采集器只在"被 kill"时发最后一批 → 小流量下日志 10 分钟才可见（本日踩过，改成 1 秒定时 flush）
- [ ] `subprocess` / `pkill -f` 的模式串匹配到自己 → 把自己杀掉（本日踩过）
- [ ] 每条日志一次 `COMMIT` → 吞吐被 fsync 钉死
- [ ] 多进程写同一 SQLite 却不设 `busy_timeout` → 高峰期丢日志
- [ ] 解析失败的行直接丢弃 → 恰恰最该看到的那条格式坏了
- [ ] 时间戳不带时区 → 跨机房/跨语言对不齐
- [ ] 报告里塞 CDN 资源 → 内网/离线环境打不开
