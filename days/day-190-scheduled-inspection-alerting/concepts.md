## 1. 调度的三种时间模型

巡检系统的第一性问题不是"怎么扫"，而是**"什么时候扫"**。三种模型，行为完全不同：

| 模型 | 下一次触发 | 长期行为 | 适用场景 |
|---|---|---|---|
| 固定延迟 fixed-delay | 上次**完成** + interval | 漂移 ≈ Σ 每次耗时 | 低频批处理、不在乎整点 |
| 固定频率 fixed-rate | 上次**开始** + interval | 漂移 ≈ Σ 每次耗时（更小，但仍累积） | 一般定时任务 |
| 网格/锚点 anchored | anchor + n × interval | **不累积漂移** | 巡检、对账、报表 |

真实数字（code/01，24 小时 / 96 个 15 分钟格子，单次任务 1–3 秒）：

`@text
fixed-delay   96 次   末次漂移 187.0s
fixed-rate    96 次   末次漂移 -17.1s（仅抖动）
`@

**为什么固定延迟一定会漂**：漂移是耗时的积分。只要单次执行有耗时，下一次的起点就往后推一点，一天 96 次就是 96 个耗时之和。想"每 15 分钟扫一次"，就必须用锚点网格，而不是"跑完再睡 15 分钟"。

### 1.1 锚点网格的两个必答题

1. **错过的格子怎么办？** 进程挂了 6 小时，恢复时是补 24 次还是补 1 次？
2. **同时刻的实例会不会撞车？** 8 个副本同一秒醒来，扫描目标会被打成 DDoS。

`@text
锚点网格：  |----|----|----|----|----|----|     每个 | 是一个 slot
            s0   s1   s2   s3   s4   s5
停机 6h 后：                                  ▲ 现在
            积压 s1..s24，全补 = catch-up storm
            grace=300s + max_catchup=1 → 只补 1 次，跳过 23 次并记账
`@

**grace（迟到容忍）的取值逻辑**：巡检的语义是"现在长什么样"，不是"历史上曾经长什么样"。迟到超过 grace 的结果已经过期，补跑只会浪费资源并制造一堆"看起来刚变化"的假告警。被跳过的格子必须写进审计表，否则监控里看不出这段缺口。

### 1.2 抖动（jitter）不是随机，是"确定的随机"

抖动必须可复现：同一个 slot 每次算出的偏移必须一样，否则重启后同一格会被当成新任务重复执行。实现上用 hash(job_id, slot) 做种子，而不是 random.random()。

`@@@@python
offset = ((hash(f"slot-{slot}") % 1000) / 1000.0 * 2 - 1) * JITTER * INTERVAL
`@@@@

实测（code/01）：8 个实例，无抖动时窗口跨度 0s（全部同一秒），±8% 抖动后跨度 85s。总工作量不变，峰值降了一个数量级。

## 2. 执行语义：至少一次、至多一次、恰好一次

| 语义 | 保证 | 代价 | 实现 |
|---|---|---|---|
| at-most-once | 最多跑一次，可能没跑 | 丢任务 | 领了就删 |
| at-least-once | 至少跑一次，可能重复 | 要幂等 | 租约 + 失败重投 |
| exactly-once（效果） | 副作用恰好一次 | 需要去重键 | 幂等写 + 唯一约束 |

分布式系统里**没有**免费的 exactly-once，只有"至少一次投递 + 幂等消费"拼出来的 exactly-once **效果**。这是本课最重要的一句话。

### 2.1 幂等键怎么设计

幂等键 = **业务语义的唯一标识**，不是请求 ID。

| 场景 | 好的键 | 坏的键 |
|---|---|---|
| 定时扫描 | scan:2026-10-20T10:00Z:assets | uuid4() |
| 告警去重 | rule|asset | rule|标题(含时间) |
| 数据入库 | (ip, port, proto) | 自增 id |

判据：**同一件事发生两次，键必须相同；两件不同的事，键必须不同。** 前者保证不重复执行，后者保证不误吞。

### 2.2 租约（lease）与崩溃恢复

`@text
worker A: claim → status=running, lease_until=now+30s
          ↓ 崩溃（没 finish）
t+30s:    worker B: claim → 命中 "running 且 lease 过期" → 接手，attempts+1
          ↓
          finish → effects 唯一键挡住第二次副作用
`@

第一版实现只查 status='pending'，崩溃任务永远卡在 running —— 这是本课真实踩到的坑（见 README 翻车实验 2）。正确条件：

`@@@@sql
WHERE (status='pending' AND visible_at<=?)
   OR (status='running' AND lease_until<=?)
`@@@@

### 2.3 退避：为什么必须加 jitter

指数退避（1s, 2s, 4s…）解决"别立刻再打"，但所有失败任务会**同步**重试，形成 thundering herd。full jitter 把等待时间摊成 uniform(0, ceiling)：

`@@@@python
ceiling = min(60, 1 * 2 ** (attempt - 1))
delay = random.uniform(0, ceiling)
`@@@@

实测退避值（code/02）：attempt 1 → 0.13s，attempt 3 → 0.54s，attempt 20 → 8.06s（封顶 60s）。

### 2.4 错误分类

- **临时错误**（连接重置、超时、503、锁冲突）→ 重试
- **永久错误**（400、404、403、参数非法）→ 立即 dead，不重试

不分类的重试会把一个参数错误放大成 3 倍流量，还会把下游的 4xx 变成自己的 5xx。

## 3. 告警降噪：五级漏斗

`@text
500 条变化
   │  ① 归一化：统一 rule / asset / severity 词表
   ▼
   │  ② 去重：fingerprint + 冷却窗口（同问题不重复打扰）
   ▼
   │  ③ 静默：维护窗口 / 已知噪声（只计数不发送）
   ▼
   │  ④ 分组：时间窗聚合，一条消息说清 N 件事
   ▼
   │  ⑤ 限流：令牌桶，超出的合并进下一条，绝不静默丢弃
   ▼
  2 条消息（实测：500 → 2）
`@

### 3.1 指纹（fingerprint）设计

指纹决定"什么算同一件事"。三种设计，三种结局（code/04，125 条事件）：

| 指纹 | 消息数 | 丢失 critical | 结论 |
|---|---|---|---|
| rule | 2 | **4** | 太粗，高危被低危吞掉 |
| rule+asset+title(含次数) | 125 | 0 | 太细，等于没降噪 |
| rule+asset + 升级放行 | 17 | 0 | 正确 |

**规则**：指纹里放"身份"（哪条规则、哪个资产），不放"描述"（第几次、什么时间、多少条）。

### 3.2 严重级升级必须穿透冷却

低危先报过 → 冷却期内的同指纹高危**必须放行**。否则会出现最坏情况：系统"安静"，因为你把唯一的真警报静音了。

### 3.3 限流不能丢数据

令牌桶满时有两个选择：丢弃（简单、丢证据）或溢出队列（复杂、可审计）。选后者，并在下一条消息里写"另有 N 条被合并"。实测：限流 4 次后，5 条仍然全部送达（delivered=5）。

## 4. 告警文案：一条消息该有什么

`@@@@json
{
  "title": "资产变更 56 条（严重 20 / 警告 0 / 提示 36）",
  "counts": {"critical": 20, "warning": 0, "info": 36},
  "total": 56,
  "items": [{"rule": "...", "asset": "10.0.2.3:3389", "severity": "critical", "title": "..."}],
  "truncated": 48
}
`@@@@

四个必备字段：**总量**（有多大）、**分级计数**（有多急）、**Top N 明细**（先看哪个）、**截断数**（还有多少没展示）。缺了 truncated，读者会以为看到的就是全部。

## 5. 一键部署：把"能跑"变成"可复现"

### 5.1 为什么需要 Compose 而不是一堆命令

手工部署的隐性状态：装了哪些依赖、端口被谁占了、上一次的容器还在不在、健康检查靠肉眼。Compose 把这些变成**声明式文件**，up / down 幂等。

### 5.2 健康检查的两种

| 类型 | 检查什么 | 例子 |
|---|---|---|
| liveness | 进程还活着吗 | HTTP /health 200 |
| readiness | 能接流量了吗 | 依赖（DB/下游）可用 |

本课 worker 用**心跳文件**做 liveness：time.time() - mtime < 20。为什么不查 HTTP？因为"活着但循环卡死"是最常见的故障，端口还在监听不代表在干活。

### 5.3 依赖顺序

`@@@@yaml
depends_on:
  sink:
    condition: service_healthy   # 不是 service_started
`@@@@

service_started 只保证容器起来了，不保证端口能连。用 service_healthy + healthcheck，才能消掉"启动竞态"这类偶发失败。

### 5.4 撤收也是交付物

部署脚本必须能把自己的痕迹擦干净：容器、网络、卷、端口。否则第三次实验就会因为 port already allocated 失败，而没人知道是上一次没清。

## 6. 验收：断言，不是肉眼

`@text
[PASS] 任务数等于差异数（重复入队被去重）   jobs=7 entries=7
[PASS] 每个任务只产生一次副作用             effects=7 dup=0
[PASS] 严重事件全部送达                     critical=2
[PASS] 消息条数受控                         messages=1
[PASS] 消息内无重复条目                     dup_items=0
`@

验收脚本必须**返回非零退出码**才算失败。打印 "OK" 但 exit 0 的脚本，在 CI 里等于没有。

## 7. 速查表

| 需求 | 做法 | 反例 |
|---|---|---|
| 不漂移 | 锚点网格 | sleep(interval) |
| 防尖峰 | 确定性抖动 | 全部整点触发 |
| 防补跑风暴 | grace + max_catchup | 全量补跑 |
| 防重复执行 | 幂等键 + UNIQUE | uuid 做键 |
| 防崩溃卡死 | 租约过期可重领 | 只查 pending |
| 防重试风暴 | 指数退避 + full jitter | 固定 1s 重试 |
| 防告警淹没 | 指纹 + 分组 + 限流 | 一条变化一条消息 |
| 防吞高危 | 升级穿透冷却 | 统一冷却 |
| 防启动竞态 | service_healthy | service_started |
| 防实验残留 | down -v + 端口校验 | 只 stop |
