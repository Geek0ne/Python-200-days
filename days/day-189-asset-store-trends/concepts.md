## 1. 资产（Asset）与自然键

**定义**：资产是"网络上可被观测的一个服务端点"，最小标识是
`(ip, port, proto)`。主机名、服务名、banner 都是**属性**，不是身份。

**为什么不用主机名**：同一 IP 可能反解出多个名字，改名、CDN、通配 DNS
都会让主机名漂移。端口和协议则是扫描器直接观测到的事实。

**为什么不用自增 id**：id 是存储层实现细节。重建库、导出再导入、
换数据库都会重新分配。用 id 做集合差，得到的"新增/消失"全是噪音。

**常见误用**：

~~~python
# 错：拿对象身份当资产身份
if old_asset is not new_asset: ...

# 对：拿自然键
if (old.ip, old.port, old.proto) != (new.ip, new.port, new.proto): ...
~~~

## 2. 当前状态表 vs 观测流水

| | 当前状态表 `assets` | 观测流水 `scan_assets` |
|---|---|---|
| 内容 | 每个自然键一行 | 每次扫描 × 每个资产一行 |
| 是否可变 | 可变（UPDATE） | 只追加（INSERT） |
| 回答的问题 | 现在暴露什么 | 某天看到了什么 |
| 查询成本 | O(1)（唯一索引） | O(天数)（按 scan_id 聚合） |
| 丢失后果 | 历史没了 | 当前状态要每次现算 |

**为什么两者都要**：
只保留当前状态，就无法回答"上周这台机器开过 6379 吗"；
只保留流水，每次告警都要扫全表求"最后一次观测"，延迟随历史线性增长。

这是 CQRS 的最小实践：**写模型记录事实，读模型服务查询**。
两层之间允许短暂不一致，但同一事务内更新可以做到强一致（本课就是这么做的）。

## 3. 快照（Snapshot）与增量（Delta）

**全量快照**：一次扫描对目标集合的完整观测。
**增量**：相邻两份快照的集合差。

为什么变更检测必须基于全量快照：

~~~text
增量扫描：本次只扫了 10.0.0.0/25
判断"10.0.0.128 消失了" → 其实只是没扫到 → 误报
~~~

**推论**：入库模块不关心扫描器内部是否增量，它要求输入是
"这次任务覆盖范围内看到的完整集合"。扫描范围本身也要作为元数据记录，
否则跨范围比较仍然会误报。

### 集合差的三种实现

| 方式 | 正确性 | 复杂度 | 适用 |
|---|---|---|---|
| 内存 `set` 差集 | 高 | O(n) | 单机、数据量适中 |
| SQL `LEFT JOIN ... IS NULL` | 高 | 依赖索引 | 数据已在库中 |
| 比较 COUNT | **低** | O(1) | 只适合监控总量，不能定位 |

本课用第一种：先把本次观测建成 `dict[key]`，再遍历库中 `state != 'gone'` 的行。
好处是可以在同一轮里处理 UPSERT、事件写入和 `miss_count`。

## 4. 变更分类与状态机

| 事件 | 前置状态 | 触发 | 是否告警 |
|---|---|---|---|
| `appeared` | 不存在 | 首次观测到键 | 是（新暴露） |
| `changed` | active/missing | service 或 banner 变化 | 视资产等级 |
| `missing` | active | 本次未观测，次数 < grace | 否 |
| `gone` | active/missing | 本次未观测，次数 ≥ grace | 是（确认下线） |
| `revived` | gone | 再次观测到 | 是（高优先级） |

状态机：

~~~text
(无) --appeared--> active --未观测--> missing --未观测×grace--> gone
                     ^                   |                        |
                     |                   +----再次观测（miss=0）--+
                     |                                            |
                     +------------revived-------------------------+
~~~

**关键设计**：`gone` 不是删除。删除会让"曾存在"这一事实消失，
也无法产生 `revived`；更糟的是，重新出现时会被当成 `appeared`，
丢掉"它曾经下线过"的审计线索。

## 5. grace 期：把抖动挡在告警之外

**定义**：连续未观测次数达到 `grace` 才把状态从 `missing` 改为 `gone`。

**为什么是次数而不是时间**：
实现简单、无需定时任务、与扫描节奏天然对齐。
**但它的语义依赖扫描频率**：每天一次时 `grace=2` 是 2 天，
每小时一次时只有 2 小时。如果扫描频率不稳定，应该改用
"`last_seen` 超过 `max_silence_hours` 才 gone"的时间口径。

**选择 grace 的方法**：

1. 统计历史抖动：端口在两次扫描间消失又出现的比例；
2. 取抖动持续时长的 P99；
3. 令 `grace × 扫描间隔 > P99`，并留一倍余量。

**代价**：确认下线变慢，资产台账会短期偏高。
对安全团队，宁可晚一天关工单，也不要一天 50 条误报。

## 6. 幂等（Idempotency）与 UPSERT

**定义**：同一输入执行多次，结果与执行一次相同。

资产入库必须幂等，因为真实链路会重试：

- 扫描任务超时后被调度器重跑；
- 消息队列至少一次投递；
- 人工补扫同一时间段。

**实现要点**：

1. 自然键上有 `UNIQUE` 约束（数据库层兜底，防并发重复）；
2. 写入用 UPSERT，而不是 `INSERT`；
3. `first_seen` 只在首次插入时写，更新时不动；
4. `scan_assets` 主键 `(scan_id, asset_id)` + `INSERT OR IGNORE`，
   同一批次重放不会重复计数。

**反例**：先 `DELETE` 当天数据再重插。
如果重跑在中途失败，会留下一个"半天"的快照，趋势出现凹坑。

## 7. 趋势口径（Metric Definition）

同一个词，不同口径会得出相反结论：

| 指标 | 口径 A | 口径 B | 差异 |
|---|---|---|---|
| 开放端口数 | 当天所有扫描之和 | 当天最后一次快照 | A 随扫描频率膨胀 |
| 新增资产 | 当天 `appeared` 事件数 | `first_seen` 落在当天 | 后者不受重扫影响 |
| 下线资产 | 当天 `gone` 数 | 当前 `state='gone'` 总数 | 前者是流量，后者是存量 |
| 变更数 | 所有事件 | 排除 `appeared`/`missing` | 后者才是"真正变化" |

**原则**：指标必须写清"时间窗口 + 聚合方式 + 数据源表"，
并固化成 SQL 视图或函数，避免每个人各算一套。

本课实现：

~~~sql
-- 每天最后一次扫描
SELECT date(started_at) AS d, MAX(id) AS last_scan
  FROM scans GROUP BY date(started_at)
~~~

## 8. 存储引擎：WAL、事务、索引

### WAL

- 读不阻塞写，写不阻塞读；
- 适合"扫描持续写入 + 看板随时查询"；
- 代价：多两个文件（`-wal`、`-shm`），备份要用 `VACUUM INTO` 或
  `sqlite3 .backup`，不能只拷主库文件。

### 事务

- 默认 autocommit：每条语句一次事务、一次 fsync；
- 批量写入应显式 `BEGIN ... COMMIT`；
- 事务过大（百万行）会长时间持锁、WAL 膨胀，建议按 1000~10000 行分批。

### 索引

- `UNIQUE(ip, port, proto)` 自动创建唯一索引，资产键查询 O(log n)；
- 过滤列（`service`、`state`、`seen_at`）按查询模式建；
- 低选择性列（`state` 只有 3 值）通常不值得单独建索引；
- 索引会让写入变慢，因为每次写要维护 B-Tree。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 自然键 | 业务上唯一标识实体的字段组合，本课为 `(ip, port, proto)` |
| 代理键 | 数据库生成的自增 id，仅用于存储 |
| 快照 | 某一时刻的完整观测集合 |
| 差集 | 两份快照之间新增/消失的键集合 |
| 水位 | 当前已处理到的扫描批次（本课用 `MAX(scan_id)`） |
| 抖动 | 资产在相邻两次扫描间短暂消失又出现 |
| 静默失败 | 不报错但结果错误，如空表被当成"零资产" |
| 口径 | 指标的计算定义，包括窗口、聚合、数据源 |
