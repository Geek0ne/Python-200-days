## 挑战 1：让报告"可签名"（★★★）

**背景**：审计报告要交付给甲方。甲方需要确认两件事：
（a）报告没被中途改过；（b）报告确实来自你的工具，而不是别人伪造的。

**要求**：
设计一个方案，让报告带上可验证的完整性证明，且**不引入第三方依赖**。

提示：标准库里有 `hashlib` 与 `hmac`。

**请回答**：
1. 哈希（`sha256`）能解决 (a) 还是 (b)？
2. 如果只加哈希，攻击者能不能伪造？为什么？
3. 要同时解决 (a)(b)，需要引入什么？（关键词：密钥的**分发**）

<details>
<summary>判定标准与参考思路</summary>

**参考思路**：
- 哈希只解决 (a)：能证明"和生成时一样"，但任何人只要重新生成就能造一份新报告
- 解决 (b) 必须用 **HMAC / 签名**，而这就绕不开"密钥怎么安全分发"这个老问题
- 关键认识：**哈希 = 完整性，签名 = 来源真实性**。很多方案把两者混为一谈，
  于是造出一个"看起来防篡改、其实可以随便伪造"的东西

**加分项**：
- 指出报告里 `generated_at` 一旦外部注入（确定性要求），
  时间戳本身就失去了"防篡改"意义 —— 它只是记录，不是证明
- 提出"报告 + 签名 + 指纹"三者一起归档，而不是只存报告

**扣分项**：
- 说"用哈希就够了"（漏掉伪造问题）
- 把密钥硬编码进容器镜像（那就等于公开了）

</details>

## 挑战 2：把确定性推到镜像层（★★★）

**背景**：同一份输入，你在两台机器上构建镜像、跑报告，产物哈希不一样。

**要求**：列出一个**完整的排查清单**，按"最可能 → 最不可能"排序，
并说明每一项怎么验证。

<details>
<summary>判定标准与参考思路</summary>

**参考排查顺序**：

1. **报告时间戳**
   验证：产物里 `generated_at` 是否一致；是否设了 `SOURCE_DATE_EPOCH`
2. **基础镜像漂移**
   验证：`docker images --digests`；是否固定到 `@sha256:...`
3. **依赖版本漂移**
   验证：`pip freeze` 对比；requirements 是否用 `==` 精确锁定
4. **文件遍历顺序**
   验证：代码里有没有 `os.listdir` / `glob` 未排序就参与渲染
5. **字典/集合迭代顺序**
   验证：模型里有没有非排序的 `json.dumps`（少用 `sort_keys` 兜底会漏字段顺序）
6. **浮点/本地化**
   验证：有没有 `locale` 相关的格式输出；有没有浮点参与哈希
7. **构建层缓存差异**
   验证：`docker build --no-cache` 两次结果是否一致

**加分项**：
- 指出"确定性地构建镜像"是独立议题（Docker 本身曾不支持可复现构建，
  需要 `SOURCE_DATE_EPOCH` + 固定 digest + 关掉时间戳写入）
- 提出在 CI 里加一条"两次构建产物哈希必须相等"的守卫

**扣分项**：
- 只说"时间戳问题"就收工（那是 2.5 节已经讲过的表层）

</details>

## 挑战 3：设计"误报反馈闭环"（★★★★）

**背景**：本课的门禁用**原始 severity** 卡，故意不看置信度（见 6.3）。
代价是：低置信度的误报会反复让 CI 变红。团队的真实反应通常是
"把 `--fail-on` 从 high 调到 critical"——**门禁名存实亡**。

**要求**：
设计一个机制，让团队可以"精确豁免某一条误报"，同时**不削弱门禁**。

**请回答**：
1. 豁免的键应该是什么？（想想稳定 id 的意义）
2. 豁免记录里必须包含哪些字段，才能防止"豁免被滥用"？
3. 豁免会不会过期？谁负责复核？

<details>
<summary>判定标准与参考思路</summary>

**参考思路**：
- 豁免键应该用 **稳定 id**（内容哈希）——这正是 2.6 节那个设计的第二个用途：
  id 稳定，豁免才能跨运行生效；用 UUID 的话豁免第二天就失效了
- 豁免记录必须包含：`id`、`rule_id`、`target`、**豁免人**、**豁免理由**、
  **豁免时间**、**复核日期**
- 必须能过期：一条"永久豁免"等于把规则删掉，只是看起来没那么明显
- 豁免应该**统计并在报告里显示**："本次报告含 3 条已豁免项" ——
  豁免数量上升本身就是风险信号

**关键认识**：门禁的敌人不是误报，是**为了消除误报而把阈值调松**。
精确豁免让"放过"这个动作**留痕、可审计、有时限**，
比调松一个全局阈值诚实得多。

**加分项**：
- 提出"豁免要有配额上限"（例如每季度 ≤5 条），超了就强制复核而不是直接放行
- 指出豁免记录本身也是审计证据，要一起归档

**扣分项**：
- 说"把置信度也加进阈值判断"（这正是 6.3 节里明确不推荐的做法，
  会打开"低置信度高危合法放过"的口子）

</details>

## 挑战 4：给报告加"变化摘要"（★★★★）

**背景**：报告越来越多，没人愿意看完整版本。真正需要的是：
**和上次比，有什么变了？**

**要求**：设计并实现一个 `--diff-against <旧报告.json>` 参数，
在报告顶部生成一段变化摘要。

**具体产出**（写进你本地练习脚本，不必提交到仓库）：
1. 顶部摘要区的结构（新增 / 已修复 / 严重度变化 / 风险分变化）
2. 处理"同一 id 但 severity 变了"这种情况的策略
3. 怎么保证这个摘要本身也是**确定的**

<details>
<summary>判定标准与参考思路</summary>

**关键点**：
- 用 `id` 做交集/差集（2.6 节）
- "同一 id 但 severity 变了"必须**单独一类**，不能算作"新增"。
  为什么？因为 id 里含 severity（`stable_id(target, rule_id, severity)`），
  severity 一变 id 就变 —— 于是它会被同时算成"新增 + 已修复"。
  **这正是本课 id 设计的一个已知边角**，能在练习里发现它，说明你真的读懂了 2.6。
  两种处理方式：
  (a) 接受它（简单，但对比噪声大）
  (b) 引入"弱 id"（只含 target + rule_id）作为辅助对比键，
      用弱 id 匹配到 → 再看 severity 是否变化
- 摘要必须确定性：所有列表排序、时间戳来自被对比的两份报告

**加分项**：
- 指出风险总分变化应区分"新增导致"与"严重度升级导致"
- 提出摘要要能解释变化原因（例如"3 条新增全部来自同一规则 → 可能是规则更新而非目标恶化"）

</details>

## 挑战 5：容器的"最小权限"你还能再砍掉什么？（★★★）

**背景**：本课已经做到非 root、只读根、无网络、cap_drop ALL、内存限额。

**要求**：再列出 3 项可进一步收紧的配置，并说明每项的**代价**。

<details>
<summary>判定标准与参考思路</summary>

**候选项**：

| 措施 | 挡住什么 | 代价 |
|:----|:--------|:----|
| `docker run --pids-limit 64` | fork 炸弹 | 几乎无（本程序是单进程） |
| seccomp 默认/自定义 profile | 危险系统调用 | 可能需要调规则（某些库用非常规 syscall） |
| 用 distroless / scratch 基镜像 | shell、包管理器 | 调试变难（没有 sh 进去看） |
| `--ulimit nofile=64` | 文件描述符耗尽 | 无（只开几个文件） |
| `--ipc=none --uts=none` | 命名空间干扰 | 无 |
| 只读挂载 + `--mount type=bind,ro` | 输入被改写 | 无 |
| 镜像签名验证（cosign / Notary） | 拉取被投毒的镜像 | 需要密钥与流程支撑 |

**关键认识**：收紧要能说出**代价**才算真的懂了。
"再加一项 `--cap-drop`"不算能力，"能指出这项收紧会让调试从 5 分钟变成 1 小时"才算。

**加分项**：
- 指出本程序**不需要** shell，所以 distroless 是合适的
  —— 但如果将来要在容器里跑扫描工具（需要 exec 子进程），就不能这么做
- 提到"最小权限要按任务的真实需求定"，而不是"照抄一份清单"

</details>

## 🎯 收官思考（四天项目总结）

四天下来，这个工具箱的形状是：

```text
Day 162  资产面   →  有哪些东西存在
Day 163  漏洞面   →  它们有什么弱点
Day 164  流量面   →  网络上实际发生了什么（且秘密不落盘）
Day 165  产出面   →  变成可交付、可复核、可门禁的证据链
```

**一个问题留给你**：如果现在有人问你
"你这个工具能保证我的系统安全吗？"

标准的、诚实的回答应该包含哪三件事？

<details>
<summary>参考</summary>

1. **不能**保证 —— 工具只覆盖它测过的范围
2. **覆盖缺口在哪** —— 主动说出 TLS 不可见、无授权账号、无 IPv6 等盲区
3. **结论有边界** —— 本次未发现问题 ≠ 没有问题，而是"在 A/B/C 范围内未发现"

任何声称"保证安全"的安全工具，都在做两件事之一：
说谎，或者把责任转移给使用者。
**一个诚实的工具的标配，是把自己的边界说清楚。**
这也是这四天里，比任何一行代码都重要的东西。

</details>
