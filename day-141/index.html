Day 141 — 爬虫监控与告警

爬虫写出来只是开始，能长期稳定跑下去才是本事。今天解决三个核心问题：怎么知道爬虫挂了？挂了怎么自动重试？挂了怎么第一时间通知到人？

一、概念解释

1.1 为什么爬虫需要监控？

爬虫是运行在"别人的地盘"上的程序，天然不稳定：

  • 目标网站改版：CSS 选择器失效、接口字段变更 → 爬到的全是空数据
  • 反爬升级：昨天还能用，今天就被封 IP / 弹验证码
  • 环境故障：代理池耗尽、磁盘写满、内存泄漏、网络抖动
  • 静默失败（最危险）：程序没报错，但抓回来的数据量从 10 万条掉到 100 条

没有监控的爬虫 = 一个你不知道什么时候已经死掉的爬虫。

监控的核心目标，按优先级排序：

优先级 目标 说明
1 数据量监控 今天抓到的数据量 vs 历史均值，骤降 = 出事
2 异常捕获 所有未处理异常必须被记录并触发告警
3 成功率/耗时 请求成功率、平均响应时间、状态码分布
4 进程存活 爬虫进程是否还在跑（心跳机制）

1.2 什么是"健康检查"？

健康检查 = 用一个独立的程序定期回答三个问题：

  1. 爬虫进程活着吗？（进程级）
  2. 爬虫还在产出数据吗？（业务级）← 最重要
  3. 产出数据的质量正常吗？（质量级，如去重率、空字段率）

关键设计原则：业务级监控 > 进程级监控。 进程活着但数据为零，比进程崩了更隐蔽、更致命。

1.3 任务失败重试

网络请求失败是常态，必须内置重试。但重试不是无脑 for 循环，要考虑：

  • 哪些错误该重试：超时、连接错误、5xx —— 这些是"暂时性错误"；4xx（如 403 封号）重试只会死得更快
  • 退避策略（Backoff）：每次重试等待时间指数增长，避免把快挂的服务打死
  • 抖动（Jitter）：多个爬虫同时重试会产生"惊群效应"，加随机抖动错开
  • 最大次数 + 死信处理：超过上限要放弃并把任务记录下来，供人工排查

1.4 通知告警（钉钉/企微）

告警的本质是Webhook：往一个 URL POST 一段 JSON，IM 机器人就会在群里发消息。

  • 钉钉：安全设置支持"自定义关键词"、"加签（HMAC-SHA256）"、"IP 白名单"
  • 企业微信：直接 POST 明文即可，最简单
  • 告警要分级：WARNING（数据量下降 30%）用 @ 提醒，CRITICAL（连续 3 次零产出）用电话/强提醒

二、原理解释

2.1 重试的指数退避算法

第 n 次重试的等待时间：

delay = base * (2 ** attempt) + random(0, jitter)

例如 base=1s：第 1 次失败等 ~1s，第 2 次等 ~2s，第 3 次等 ~4s，第 4 次等 ~8s。

为什么要指数增长？
- 目标服务过载时，立即重试等于火上浇油
- 指数退避给了服务恢复的"喘息时间"
- 加随机抖动（jitter）是为了避免多个客户端同步重试造成周期性流量尖峰（惊群）

2.2 心跳机制

爬虫主进程
   │  每 30s
   ├──写入──→ heartbeat 文件 / Redis key（带时间戳）
   │
监控进程（独立运行）
   │  每 60s 检查一次
   ├──读──→ 时间戳距今 > 90s ？→ 触发告警

心跳的存储介质选择：

  • 文件：最简单，适合单机（写 /tmp/spider.heartbeat）
  • Redis：SET spider:heartbeat <ts> EX 120，天然带过期，适合分布式
  • 数据库：顺带记录统计信息，但耦合较重

2.3 异常监控的分层捕获

请求层    → 重试装饰器捕获（requests exceptions）
解析层    → try/except 包住每个字段提取，记入"解析失败计数"
业务层    → 数据量断言（今日数据 < 阈值 → 告警）
进程层    → 全局 sys.excepthook 捕获未知异常，崩溃前发出告警

为什么要分层？ 顶层一个大 try/except 会吞掉所有细节，你只知道"挂了"，不知道"挂在哪一层"。

2.4 钉钉加签原理

python
timestamp = str(round(time.time() * 1000))
secret_enc = secret.encode('utf-8')
string_to_sign = f"{timestamp}\n{secret}"
sign = base64.b64encode(
    hmac.new(secret_enc, string_to_sign.encode('utf-8'), digestmod=hashlib.sha256).digest()
)
url = f"{webhook}&timestamp={timestamp}&sign={quote_plus(sign)}"

钉钉服务器用同样的 secret 重新计算签名并比对，防止 webhook URL 泄露后被任意人调用。

三、API 速查表

3.1 requests / urllib3 重试

python
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

retry = Retry(
    total=3,                    # 总重试次数
    backoff_factor=1,           # 退避基数：{backoff_factor} * (2 ** (n-1))
    status_forcelist=[500, 502, 503, 504],  # 对这些状态码重试
    allowed_methods=["GET", "HEAD"],        # 只对幂等方法重试（重要！）
)
session.mount("http://", HTTPAdapter(max_retries=retry))
session.mount("https://", HTTPAdapter(max_retries=retry))

六、思考题

  1. 为什么 Retry 的 allowed_methods 默认只对 GET/HEAD 重试？如果对 POST 重试会有什么风险？（提示：幂等性）

参考答案

关键是幂等性：同一操作执行一次和执行多次，效果相同。GET/HEAD 只读取、不改变服务器状态，重试安全；POST 通常创建资源、是非幂等的（下单、支付、发评论）。

对 POST 重试的风险：请求其实已成功，但响应在网络中丢失（超时），客户端以为失败而重试 → 服务器创建两次 → 重复下单/重复扣款/重复数据。"超时 ≠ 失败"是核心。

所以默认只重试幂等方法；若必须重试 POST，业务侧要有幂等键（idempotency key，服务器按键去重），或确认接口本身幂等。

小例子：支付接口超时后重试，没有幂等键会扣两次款；带上订单号幂等键，第二次会返回"已处理"。
2. 你的爬虫连续 7 天每天正常产出 10 万条数据，第 8 天突然变成 9.5 万条。这算异常吗？如何设计一个不误报、不漏报的阈值？

参考答案

单日下跌 5% 不一定是异常（周末、目标站内容减少、正常波动都可能），但值得"关注"。设计思路：滚动基线（近 7 天同星期均值）+ 动态阈值 max(3σ, 保底比例) + 连续 N 期才告警 + 分级。用标准库演示：

python
import statistics

def threshold(history, floor_pct=0.05):
    mean = statistics.mean(history)
    std = statistics.pstdev(history)
    # 3σ 与“均值×保底比例”取更宽松者，避免历史方差极小时误报
    return mean - max(3 * std, floor_pct * mean)

# 场景1：历史产出极稳定（标准差=0），纯 3σ 会让任何下跌都报警
stable = [100000] * 7
print("稳定历史: 纯3σ阈值 =", statistics.mean(stable) - 3 * statistics.pstdev(stable))
print("稳定历史: 加5%保底后的阈值 =", threshold(stable))
print("今天 99500（正常波动）会报警吗?", 99500 < threshold(stable))

# 场景2：历史有正常波动，今天 95000（下跌约 5%）
history = [100000, 99000, 101000, 100500, 99500, 100000, 100200]
t = threshold(history)
print(f"波动历史: 均值 {statistics.mean(history):.0f}, 阈值 {t:.0f}")
print("今天 95000 会报警吗?", 95000 < t)

预期输出：

稳定历史: 纯3σ阈值 = 100000.0
稳定历史: 加5%保底后的阈值 = 95000.0
今天 99500（正常波动）会报警吗? False
波动历史: 均值 100029, 阈值 95027
今天 95000 会报警吗? True

解读：历史极稳定时 σ=0，纯 3σ 会让任何下跌都误报，加 5% 保底后正常波动不报警；95000 略低于阈值 95027 → 触发 WARNING，若下一期仍低再升级为 CRITICAL。这样既不误报正常波动，也不漏报真实骤降。

⚠️ 注意：要把节假日/大促等已知异常排除出基线，否则阈值会被"污染"。
3. 告警抑制（同一故障 1 小时内只发一次）为什么重要？如果不做抑制，会发生什么连锁灾难？

参考答案

因为同一故障会在短时间触发海量告警（每个请求失败一次就发一条），不做抑制会引发连锁灾难：

  1. 告警风暴：每分钟几百条消息，值班人手机被打爆，真正重要的告警被淹没；
  2. IM 限频封禁：钉钉/企微机器人有频率限制（如 20 条/分钟），超了直接被封，后续真实告警发不出去；
  3. 告警疲劳："狼来了"效应，人开始忽略所有告警，监控失去意义；
  4. 下游压力：告警系统本身成为故障源。

抑制策略：同一指纹（spider + 错误类型）1 小时内只发一次，并聚合计数（"过去 1 小时失败 500 次"）；状态变化时升级（恢复通知、恶化升级）；不同故障互不抑制。

小例子：代理池耗尽导致所有请求 403，不抑制的话每分钟上万条告警，机器人被封，值班人反而看不到任何有用信息。
4. 心跳机制中，如果监控进程自己也挂了，谁来监控监控者？这种"递归监控"问题在工业界一般怎么解决？

参考答案

这是"谁来监督监督者"的问题，无限递归不现实，工业界收敛到"互相监督 + 外部锚点"：

  1. 互相监控（watchdog 对）：两个监控进程互监心跳，任一挂了另一个报警；
  2. 外部死人开关（dead man's switch）：监控进程定期向外部独立服务（healthchecks.io、云监控、另一台机器的 cron）"报平安"，外部服务超时没收到就告警——"没消息就是告警"，不依赖被监控者自觉；
  3. 平台级兜底：云厂商的基础设施监控（主机宕机、进程退出）作为最后防线，独立于业务监控；
  4. 多通道冗余：告警同时走多个独立通道，一个挂了不影响其他。

本质：把"最终裁判"放到被监控系统之外，用"超时无心跳"代替"主动报错"。

小例子：监控进程每 5 分钟 ping 一次 healthchecks.io，一旦它自己挂了，healthchecks.io 发现超时便发邮件告警。
5. 数据库中爬虫写入成功，但字段全是空字符串——这属于哪一层的异常？应该在哪一层捕获？

参考答案

这是静默失败：请求层 200、解析层不报错（选择器返回空而非异常）、写库也成功——每层都"看起来正常"，但数据无效。它属于数据质量/业务层异常。

应该在解析层 + 清洗层捕获：① 解析层做字段级校验——必填字段为空就记"解析失败"计数（而非静默存空），失败率超阈值告警；② 清洗层（Pipeline P1）做 schema 校验——必填非空、类型正确，不合格 DropItem + 计数，绝不让空数据入库；③ 业务层用空字段率、产出量对比做最后兜底。

根因通常是目标站改版/反爬返回假页面，所以还要监控"响应内容指纹"（页面结构突变检测）。

小例子：价格选择器失效返回 ""，清洗层断言 price 非空 → DropItem 并计数，日报显示"price 缺失率 100%"，立刻定位，而不是等分析时才发现。
