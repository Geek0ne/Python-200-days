一、概念解释

1. 为什么要"预测"而不是继续写 if

规则能覆盖显式拒绝：403、429、验证码、JS 挑战。但真实风控里最贵的是软封——
服务器返回 200，页面正常渲染，内容却是空的或是个"请稍后再试"。

硬封：403 + WAF 页面        → if status == 403: 停     ✅ 规则能抓
限速：429 + Retry-After     → if 429: 退避             ✅ 规则能抓
软封：200 + 空壳 + 正常头   → if ???: ???              ❌ 没有单点特征

软封只能靠多个弱信号的组合：响应体异常小、延迟偏高、响应头偏少、偶发验证码。
这就是分类问题：输入一行特征，输出"这一页还能不能继续抓"的概率。

为什么不用大模型？ 每抓一页调一次 LLM，成本是每千页几块钱、延迟是几百毫秒，
而逻辑回归是每页 7 微秒、零边际成本、系数可解释。这类高频二分类的正确解法是
特征工程 + 轻量模型，LLM 适合的是低频、需要语义理解的环节（比如判断页面主题）。

2. 特征选择的原则：只要"决策时就能拿到"的

FEATURES 里的 10 个字段全部来自响应本身：状态码、响应体大小、延迟、验证码、
Retry-After、WAF cookie、响应头数量、JS 挑战、重定向跳数、UA 是否命中爬虫库。

反面例子是 block_page_title、waf_reason 这类字段——它们只在被拦之后才存在，
拿它们训练等于让模型抄答案。本次实测（见实验 1 第 3 节）把生成器的隐藏变量
_propensity 加进去，AUC 从 0.9299 抬到 0.9340：增益只有 +0.0041，因为这份数据里
10 个特征本身已经很强。增益小不代表没风险——换成弱特征数据集，同一个字段能让
离线 AUC 虚高 0.2–0.3，而你在离线阶段完全看不出来。

3. 类别不平衡与代价不对称

正类（需要停抓）只占 25.4%。如果模型全判"安全"，accuracy 也有 74.6%，但一条软封都抓不到。
所以要看的指标是 precision / recall / AUC，而不是 accuracy。

更关键的是两类错误的代价不同：

  • 误报（正常页判成被封）→ 少抓几页，代价 1
  • 漏报（被封了还在抓）→ 继续撞风控，可能整段 IP 段被封，代价 5

阈值 0.5 是数学默认值，不是业务最优值。实测把阈值下调到 0.34，总代价从 194 降到 144。

4. 去重：精确哈希为什么不够

转载场景里，同一篇文章会被改标题前缀、换标点、加推广尾巴。SHA256 对这种改动
完全无感——一个字节不同，哈希就完全不同。实测精确哈希召回只有 0.164。

SimHash 的思路是把文档压成 64 位指纹：内容相近 → 指纹只差几位。
于是"是否重复"变成"汉明距离是否 ≤ k"。代价是 k 必须自己定：

  • k 太小 → 召回低（改几个词就抓不到）
  • k 太大 → 精度崩（无关文档也撞上）

而 k 的合适值随文档长度变化：174 token 的文档最优 k=10，10 token 的商品标题
k=3 召回只有 3%。所以生产系统里 k 是按长度分层的参数，不是常数。

5. 管道：分阶段是为了"错误可定位"

把所有逻辑塞进一个函数，出错时你只知道"结果不对"。分成
采集 → 清洗 → 抽取 → 去重 → 质检 → 入库 六段之后，每一段都有明确的输入输出计数，
脏数据在哪一段消失、因为什么消失，一目了然。

配套的两条硬规则：

  1. 脏数据不静默丢：进 quarantine 表并带 reason code，否则你永远不知道丢了多少。
  2. 入库必须幂等：同一批数据跑两遍，行数必须一样。但注意——幂等只保证可重复，
    不保证正确（Day 194 的 URL 规范化事故就是"幂等但错"）。

二、原理深入

1. 逻辑回归：从线性打分到概率

模型先算一个线性分：z = w·x + b，再用 sigmoid 压到 (0,1)：

p = 1 / (1 + e^(-z))

训练目标是最小化交叉熵（加 L2）：

L = -(1/n) Σ [ y·log(p) + (1-y)·log(1-p) ] + (λ/2)·||w||²

梯度很干净：

∂L/∂w = (1/n)·Xᵀ(p - y) + λ·w
∂L/∂b = mean(p - y)

代码里就是这 4 行，1500 轮批量梯度下降，在 2100×10 的训练集上 156 ms 收敛，
loss 从 0.6932（等价于瞎猜）降到 0.2370。

2. 为什么必须先标准化

body_len 在 10⁵ 量级，status_code 只有 3 位。不标准化时：

  • 梯度里 body_len 方向的步长远大于其它维度
  • 同一个学习率下，小量纲特征几乎不动，大量纲特征来回震荡

实测证据：第一次跑 sklearn 对照时忘了标准化，lbfgs 直接报
failed to converge after 1000 iterations，还贴心地提示 "You might also want to scale the data"。
把 StandardScaler 放进 Pipeline 后，5 折交叉验证一次通过，AUC 0.9279 ± 0.0082。

另外一条容易忽略的规矩：标准化统计量只能来自训练集。用全量数据算均值方差，
测试集的信息就漏进了训练过程。

3. SimHash 的位运算

对每个 token 取一个稳定的 64 位哈希（必须用 blake2b/sha，不能用内置 hash()——
它受 PYTHONHASHSEED 影响，跨进程不可复现），然后逐位投票：

for each token t with weight w_t:
    for bit i in 0..63:
        votes[i] += +w_t if (hash(t) >> i) & 1 else -w_t
fingerprint = Σ (1 << i) for votes[i] > 0

两篇文档改了几个词，只有那几位附近的投票会翻转，所以距离小。

中文没有空格，本课用字符二元组（"新能源" → 新能/能源），零依赖且对未登录词鲁棒。
英文和数字用 [a-z0-9]+ 切词。

4. 鸽巢分桶：把 n² 变成候选集

把 64 位切成 bands 段。若两篇文档距离 ≤ bands-1，那么至少有一段完全相同
（因为最多只有 bands-1 位不同，不可能每段都被污染）。于是只需查"同段同值"的桶。

实测代价（1200 篇）：

bands 每段位宽 保证召回的 k 平均候选/篇 候选对 与全量比对
4 16 3 1.5 285 ✅ 一致
8 8 7 1.8 454 ✅ 一致

段越多 → 保证阈值越高，但每段取值空间越小、桶里越挤。这就是取舍点。

5. 两阶段：粗筛 + 精排

单靠 SimHash 阈值在 1200 篇上是这样的曲线：

k=3   P=1.000 R=0.539    ← 一个都不敢误报，但漏一半
k=10  P=0.923 R=0.970    ← 召回够了，误报 43 对
k=15  P=0.153 R=1.000    ← 全召回，但精度崩了

正确做法是分工：SimHash 只负责把 719,400 对压到 454 对候选，
最终判定交给 Jaccard（token 集合交并比 ≥ 0.6）。实测：

候选对 454 / 719,400（0.06%）
precision=1.000 recall=0.853 f1=0.920
误报 0 / 漏报 78，耗时 127 ms

6. 质量门禁：只写"能明确判定错"的规则

规则分两类：

  • 可判定：标题为空、价格不是数字、价格 ≤ 0、日期格式不对、正文 < 50 字、乱码 → 直接拦
  • 需判断：内容是否有价值、图片是否清晰、描述是否合规 → 不进自动门禁，进人工队列

本课 8 条规则全部属于第一类，误报率可控（自检里用一条正常记录验证"不误报"）。

乱码检测是个例外，它天生是启发式：

信号 1：出现 U+FFFD 或 Ã. / â€ / ï¿½ 组合
信号 2：Latin-1 补充区字符占比 ≥ 15%
信号 3：整段能用 cp1252 编码、再用 utf-8 解码得到汉字（可逆修复）

阈值取 0.15 是刻意的：取 0.05 会把正常法语（Le café crème est très bon）当成乱码隔离。

- 精确哈希召回 0.164，转载场景不可用；

无关标题的误判升到 2.30%——短文本该走集合相似度或规则。

六、翻车实验

这一节是本次编写时真实踩到的坑，按发生顺序记录。

翻车 1：SQLite 存不下 64 位哈希

现象：

OverflowError: Python int too large to convert to SQLite INTEGER

假设：SimHash 是 64 位，SQLite INTEGER 也是 64 位，应该能存。

验证：sqlite3 的 INTEGER 是有符号 64 位（−2⁶³ ~ 2⁶³−1），
而 SimHash 是无符号 64 位（0 ~ 2⁶⁴−1）。超过 2⁶³ 的值直接溢出。

根因：无符号/有符号边界没对齐。

修复：入库前 hash_to_signed() 减 2⁶⁴，读出来后 signed_to_hash() 加回去，
并加了 0、1、2⁶³−1、2⁶³、2⁶⁴−1 五个边界的往返自检。

复测：自检 5 项全过，3000 条全部入库。

翻车 2：整页文本去重 → 80.6% 被误判重复

现象：第一次跑管道，3000 条里 2419 条被判重复（80.6%），而注入的重复只有 8%。

假设 A：SimHash 阈值太大。把 k 从 7 降到 3 试了一下，召回掉光，误判只降到 70%+。
假设 B：Jaccard 阈值太低。调到 0.8 后误判仍高。

验证：打印两篇"被判重复"的正文前 120 字，发现导航、价格、版权声明、
模板句全都参与相似度计算，正文只有一小段不同。

根因：去重对象选错了——拿"整页 clean_html 之后的文本"做哈希。
站点模板的占比远大于正文差异。

修复：新增 extract_body()，只取 <article> 容器清洗后参与去重。

复测：仍 89.2%——因为我的生成器正文复用同一个句子池，正文本身也高度雷同。
进一步把正文改成"随机 5 个片段 + 6 个唯一 SKU"，降到 11.6%（注入 8% + 模板碰撞）。
同时暴露了一个新问题：TEXT_TOO_SHORT 从 0 涨到 291——正文抽取后，
"空壳页"终于现形了（此前靠导航文字蒙混过关）。这是修复带来的正确结果。

翻车 3：我自己的语料把 Jaccard 指标搞失真了

现象：给去重语料第一次做评估时，纯 Jaccard 的 precision 只有 0.006。

假设：Jaccard 阈值 0.6 太低。

验证：抽 20,000 对无关文档算 Jaccard，中位数 0.55、p90 0.75——
无关文档本来就高度相似。

根因：生成器只用了 6 个模板句子，词汇量太小。错的是语料，不是算法。

修复：改成 40 个片段的池子、每篇抽 7–10 段。修复后无关对 Jaccard 中位数降到 0.13，
真重复对中位数 0.99，指标才有意义。

教训：当指标看起来"荒谬地差"时，先怀疑评估集，再怀疑算法。

翻车 4：sklearn 不收敛（其实是没标准化）

现象：lbfgs failed to converge after 1000 iterations，五条一模一样的警告刷屏。

根因：直接把原始量纲的 X 喂给 LogisticRegression。

修复：make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000))，
并用 warnings.simplefilter("error") 让收敛警告直接抛异常——警告刷屏然后继续跑，
是最容易骗过自己的做法。

七、思考题

  1. 你的规则基线在测试集上 F1 是 0.55，模型是 0.90。上线后模型真的会更好吗？
    需要额外验证哪三件事？

参考答案

不一定。测试集 F1 0.90 只说明「在这批离线数据上」模型更好，上线后可能翻车。需要额外验证三件事：

  1. 分布是否漂移（distribution shift，线上数据与训练/测试数据分布不一致）：线上真实流量的特征分布是否和测试集一致。测试集往往是历史采样，上线后用户/内容变了，0.90 会掉。要用线上影子流量或小流量灰度对比。
  2. 特征是否泄漏、线上线下一致：训练时用的特征线上能否实时拿到、口径是否一致。若测试集混入了「未来信息」或线上取不到的字段，离线高分是假象。
  3. 阈值与代价是否校准：F1 默认 0.5 阈值，但业务上误杀/漏放代价不同。要按业务代价选阈值，看精确率/召回率各自的绝对值，而不是只盯一个 F1；还要确认 0.55 与 0.90 是同一测试集、同一口径下比出来的。

💡 提示：先小流量灰度 + 线上监控，确认指标不掉再全量；离线高分 ≠ 线上更好。

  1. 为什么 SimHash 的 k 要随文档长度变化？请用"token 数 → 单 token 权重的期望位移"
    这个角度解释，并设计一个分长度分桶的方案。

参考答案

SimHash 把每个 token 哈希成 64 位、按位投票（+1/−1）累加，最后取符号。某一位的最终值是所有 token 在该位投票的「净和」。改一个 token，相当于把它的投票翻转，对每一位净和造成约 ±2 的位移。文档越短（token 数 n 小），单 token 权重 1/n 越大，这一位移越容易把某位符号翻转 → 汉明距离大；文档越长，单 token 权重越小，净和「惯性」越大，改一个 token 很难翻位 → 汉明距离小。所以固定 k 对短文本太松（漏判）、对长文本太紧（误判），k 必须随长度变化。

python
import hashlib, re

def tokens(text):
    toks = re.findall(r"[a-z0-9]+", text.lower())
    han = re.findall(r"[\u4e00-\u9fff]", text)
    toks += ["".join(pair) for pair in zip(han, han[1:])]   # 中文用相邻二字组
    return toks

def simhash(text, bits=64):
    votes = [0]*bits
    for t in tokens(text):
        h = int.from_bytes(hashlib.blake2b(t.encode(), digest_size=8).digest(), "big")
        for i in range(bits):
            votes[i] += 1 if (h >> i) & 1 else -1   # 按位投票
    fp = 0
    for i in range(bits):
        if votes[i] > 0:
            fp |= (1 << i)
    return fp

def hamming(a, b):
    return bin(a ^ b).count("1")

short_a = "无线蓝牙耳机降噪运动跑步防水黑色"
short_b = "无线蓝牙耳机降噪运动跑步防水白色"   # 只改一个词

        "深度学习模型训练流程详解"
        "分布式系统一致性协议比较"
        "数据管道清洗与质量门禁"

        "加密算法与密钥轮换实践"
        "开源协作补丁提交流程"
        "技术写作可复现性契约"

        "并发模型与全局解释器锁")
long_a = base
long_b = base.replace("续航", "续航力", 1)     # 长文里只改一处
print(f"短文本 token 数 = {len(tokens(short_a))}，改一个词后汉明距离 = {hamming(simhash(short_a), simhash(short_b))}")
print(f"长文本 token 数 = {len(tokens(long_a))}，改一处后汉明距离 = {hamming(simhash(long_a), simhash(long_b))}")

长文本 token 数 = 110，改一处后汉明距离 = 3

同样「改一处」，15 个 token 的短文本汉明距离高达 14，110 个 token 的长文本只有 3——直观印证了单 token 权重随长度衰减。分长度分桶方案：按 token 数分桶（如 <30、30–100、>100），每桶用不同 k（短桶 k 大、长桶 k 小），或按桶建独立 bands 索引；也可把 k 设成随 n 单调递减的函数。

  1. 分桶索引 bands=8 保证 k≤7 的召回。如果业务需要 k=15 且不能用全量比对，
    你会怎么改？（提示：多个排列、多组 bands）

参考答案

靠鸽巢原理：把 64 位分成 b 段，若两指纹汉明距离 ≤ k，只要 b > k，就至少有一段完全相同（k 个差异位最多落在 k 段里，b>k 时必有一段无差异）。bands=8 只能保证 k≤7；要 k=15 就得 b≥16，即 bands=16（每段 4 位）。代价是段更短、随机碰撞概率上升、候选对变多，后续精确比对量增大。

python
import random

def bands_match(a, b, bands):
    width = 64 // bands
    for i in range(bands):
        mask = ((1 << width) - 1) << (i*width)
        if (a & mask) == (b & mask):   # 只要有一段完全相同就是候选
            return True
    return False

rng = random.Random(7)
N = 2000
hit8 = hit16 = 0
for _ in range(N):
    a = rng.getrandbits(64)
    b = a
    for bit in rng.sample(range(64), 15):   # 制造恰好 15 位差异
        b ^= (1 << bit)
    assert bin(a ^ b).count("1") == 15
    hit8 += bands_match(a, b, 8)
    hit16 += bands_match(a, b, 16)
print(f"距离=15 的 {N} 对指纹：")
print(f"  bands=8 （每段8位，保证 k≤7）：至少一段相同比例 = {hit8/N:.3f}")
print(f"  bands=16（每段4位，保证 k≤15）：至少一段相同比例 = {hit16/N:.3f}")

预期输出：

距离=15 的 2000 对指纹：
  bands=8 （每段8位，保证 k≤7）：至少一段相同比例 = 0.636
  bands=16（每段4位，保证 k≤15）：至少一段相同比例 = 1.000

bands=8 对 k=15 只有约 63.6% 召回（漏掉 36%），bands=16 达到 100%。所以业务要 k=15 就把 bands 提到 16，再用精确汉明距离复核候选；若还要兼顾不同 k，可建多组不同 bands/排列的索引取并集（即提示说的「多个排列、多组 bands」）。

  1. 质量门禁把 TEXT_TOO_SHORT 设为 50 字。如果目标站点有大量"短公告"（20 字但有效），

参考答案

一刀切 50 字会把大量 20 字的有效短公告全部判 TEXT_TOO_SHORT 误杀。规则应按内容类型设不同阈值（公告短、文章长），并结合「标题非空、含有效信息」等多信号，而不是只看长度。

def check_record(rec, min_len):

    if not rec.get("title"):

  1. 幂等 ≠ 正确。请构造一个"重跑结果一致但数据错误"的管道，并给出能在 CI 里自动发现它的断言。

参考答案

幂等只保证「重跑结果一致」，不保证「结果正确」。一个把 URL 所有 query 参数都剥掉的规范化管道，重跑永远一致（幂等），却把 ?sku=blue 和 ?sku=red 两个不同商品页压成同一个 key，静默丢数据。CI 里要加「与真值对照」的断言，而不是只测幂等。

python
from urllib.parse import urlsplit, urlunsplit, parse_qsl, urlencode

TRACK = {"utm_source","utm_medium","utm_campaign","spm","ref","from"}
def canon_legacy(url):           # 错误：剥掉所有 query
    s = urlsplit(url)
    return urlunsplit((s.scheme, s.netloc, s.path, "", ""))
def canon_fixed(url):            # 正确：只剥跟踪参数，保留业务参数并排序
    s = urlsplit(url)
    q = sorted((k,v) for k,v in parse_qsl(s.query) if k not in TRACK)
    return urlunsplit((s.scheme, s.netloc, s.path, urlencode(q), ""))

urls = [
    "https://shop.example.com/product/106?sku=blue&utm_source=ad",
    "https://shop.example.com/product/106?sku=red&utm_source=ad",
    "https://shop.example.com/product/107?sku=green",
    "https://shop.example.com/product/107?sku=yellow",
]
truth = {canon_fixed(u) for u in urls}
legacy1 = {canon_legacy(u) for u in urls}
legacy2 = {canon_legacy(u) for u in urls}
print(f"旧规则 key 数={len(legacy1)}，重跑={len(legacy2)}，幂等={legacy1==legacy2}")
print(f"真实页面数={len(truth)}")
try:
    assert len(legacy1) == len(truth)   # CI 断言：与真值对照
    print("CI: 通过")
except AssertionError:
    print(f"CI 断言失败：旧规则把 {len(truth)} 个真实页面压成 {len(legacy1)} 个 key，"
          f"静默丢失 {len(truth)-len(legacy1)} 个（重跑仍一致 → 幂等但错误）")
fixed1 = {canon_fixed(u) for u in urls}
print(f"新规则 key 数={len(fixed1)}，等于真实页面={len(fixed1)==len(truth)}")

预期输出：

旧规则 key 数=2，重跑=2，幂等=True
真实页面数=4
CI 断言失败：旧规则把 4 个真实页面压成 2 个 key，静默丢失 2 个（重跑仍一致 → 幂等但错误）
新规则 key 数=4，等于真实页面=True

旧管道幂等（重跑都是 2 个 key）但错误（真实有 4 个页面）。CI 里只断言「重跑一致」会放行；加一条「key 数 == 真值页面数」的断言就能自动抓住静默丢失。修复后规范化只剥跟踪参数、保留 sku 等业务参数，key 数恢复为 4。
