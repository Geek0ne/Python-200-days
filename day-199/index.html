一、概念解释

1.1 技术写作的读者模型：一个不在场的人

写代码时，你和执行环境在同一个闭环里：跑一下就知道对不对。
写作打破了这个闭环——读者执行的是你的文字，不是你的程序。

所以技术写作的所有规范，本质上都在补偿"作者不在场"这件事：

  • 环境指纹 → 补偿"我不知道你的机器"
  • 完整命令 → 补偿"我看不到你的终端"
  • 真实输出 → 补偿"我没法验证你说的是不是想象"
  • 结论先行 → 补偿"我随时可能关掉页面"

一句话：技术文章是把一次私人实验，改写成别人可执行的指令。

1.2 信息结构：结论先行，证据分层

技术读者不是来听故事的，是来取结论的。所以结构上要满足"三层可退出"：

第 1 层  标题 + 首段      → 30 秒判断：这篇和我有关吗
第 2 层  小标题 + 表格     → 3 分钟扫读：结论是什么
第 3 层  实验手册 + 代码   → 30 分钟精读：怎么复现

任何一层都应该是自洽的：只读第 2 层的人，也能拿走可用的结论。
这就是为什么"实验手册"要独立成章，而不是散落在正文叙述里。

1.3 可复现性契约：五个字段缺一不可

"我测过"不是证据，"这些条件下我测到这些数字"才是。最小契约：

字段 回答什么 缺失后果
环境 哪台机器、哪个版本 读者无法迁移结论
命令 到底跑了什么 读者只能猜
样本量 跑了几次、取哪个统计量 单次数字可能是噪声
原始输出 stdout/stderr 原文 无法判断是否被美化
输出指纹 哈希是否稳定 无法判断结果是否随机

02-repro-card.py 就是把这张表变成一条命令：它执行命令 N 次，记录环境指纹、
耗时分布、每次 stdout 的 sha256，并给出"输出是否可复现""计时是否可信"两个判定。

1.4 断言分级：不是所有句子都需要实验

写作最耗时的误区，是给每句话都找证据。实际上句子分三级，证据要求不同：

级别 例子 需要什么
事实 "Python 3.12 的 dict 保持插入序" 出处或一行可跑的验证
推断 "这个写法在热路径上更省" 说明推理链 + 至少一次测量
观点 "我不喜欢这个 API" 说清立场即可，不要伪装成事实

体检器拦不住你写观点，但它能拦住把观点写成事实——这正是"显然"这类词的危害：
它把一个未经证明的判断，伪装成了共识。

1.5 为什么用 Markdown 而不是 Word

不是因为好看，而是因为可计算：

  • 结构可解析 → 能做标题层级检查、TOC、锚点
  • 纯文本 → diff 可读、能进 git、能被 lint
  • 语法少 → 渲染器可以自己写，零依赖

今天的体检器、构建器都建立在"Markdown 是可解析的结构，而非排版格式"这个前提上。

1.6 静态站：把发布成本压到零

技术博客的访问曲线是长尾的：发布当天几十次，之后每月几次。
为这种负载上数据库和框架，是典型的过度工程。

静态站的取舍很清楚：

  • 得到：零运行时、零漏洞面、CDN 直接托管、构建产物可 diff
  • 放弃：评论、搜索、动态聚合（都能用外部服务补）

03-article-build.py 用 380 行做到：front matter 解析、Markdown 子集渲染、
TOC 锚点、阅读时长、首页、RSS、.nojekyll。

1.7 写作的反馈回路

写 → 体检（结构） → 实测（数字） → 发布 → 读者复现 → 修正
      ↑______________________________________________|

体检器和实验卡片只覆盖前两步。真正的质量来自第四步：有人照着你写的跑了一遍。
所以文章里要留下"怎么告诉我它跑不通"的入口（仓库 issue、邮箱），这是写作的一部分，不是客服。

二、原理解释

2.1 为什么"显然"是一种认知负担转移

"显然 X" 的信息量不是 X，而是"我判断 X 不需要解释"。读者收到的是两件事：

  1. 一个未证明的结论；
  2. 一个"你不该问"的暗示。

第二件更贵：它让读者要么接受一个黑箱，要么自己补证明。技术写作里，
任何让读者补证明的句子，都应该被删掉或改写。

改写模板：

  • 差：显然这样更快（读者无法据此行动）
  • 好：在 30KB 输入、重复 5 次、取中位数的条件下，方案 B 比 A 快 12.4 ms

2.2 代码围栏状态机：一个 continue 决定工具的死活

Markdown 的 # 既是标题标记，也是 Python/shell 的注释符。所以解析器必须是状态机：

       +--------------+  遇到围栏     +--------------+
       |  普通文本态   | -----------> |   代码块态    |
       |  解析标题/列表 | <----------- |  原样收集     |
       +--------------+  遇到围栏     +--------------+

实现只有六行，但漏掉 if in_fence: continue 就会让代码里的每个 # 注释 变成一级标题：

python
m = FENCE_RE.match(line)
if m:
    if not in_fence:
        in_fence = True
        if not m.group(2):
            add("E003", "error", i, "代码块没有标注语言")
    else:
        in_fence = False
    continue
if in_fence:
    continue   # 这一行是地基

体检器的自测里专门有一条反例：代码块内的 # 这是注释，不是标题 不允许触发 E001。

2.3 为什么数字必须带条件：噪声的三个来源

任何一次计时都混着三种成分：

来源 表现 对策
固定成本 解释器启动、import 报告时说明含不含启动
调度抖动 同机其他进程抢占 重复 N 次取中位数
真实差异 你要测的那部分 用相对差而不是绝对值

今天的实测里，30KB 输入的极差/中位是 22.8%，636KB 只有 12.6%。
如果只跑一次 30KB，完全可能把调度抖动当成"优化生效"。

2.4 实测：固定成本约 17 ms

三档输入的中位数：44.06 / 59.18 / 130.84 ms，字符数 30,483 / 156,684 / 636,684。

  • 30KB → 156KB（同一台机器、5 次取中位数）：字符 ×5.1，耗时 ×1.34
  • 156KB → 636KB（同样条件）：字符 ×4.1，耗时 ×2.21

第一段明显"不线性"，差值就是固定成本：设 t = a + b * chars，
第二段给出 b ≈ 0.155 微秒/字符，代回第一段得 a ≈ 17 ms（含解释器启动与 import）。
这个估算不精确，但它解释了为什么小文件上的百分比噪声更大——分母太小。

2.5 锚点一致性：TOC 和标题必须由同一个函数生成

第一版我用 slugify() 同时生成文件名和标题 id，结果中文标题被转成 post-a15a2f6c：
技术上能用，但读者拿到的 URL 是一串哈希，且自测里 TOC 与标题 id 对不上
（TOC 用原文、id 用哈希）。

修正：拆成两个函数，职责分开。

  • anchor_id()：给页面内锚点用，保留中文，只折叠空白、去掉标点
  • slugify()：给文件名/URL 用，ASCII 化，纯中文时用稳定哈希兜底

教训：一个函数服务两种用途，最后一定有一种被牺牲。

2.6 转义顺序：先 escape，再替换标记

行内渲染必须严格按这个顺序：

原文 → html.escape() → 识别行内代码/粗体/链接 → 输出 HTML

反过来（先替换再转义）会把自己的 <code> 标签转义掉；而只转义正文不转义代码块，
则代码里的 <script> 会真的执行。自测里有两行专门验证这件事：

python
check("&lt;script&gt;" in frag, "正文里的 <script> 被转义（不执行）")
check("x = 1 &lt; 2" in frag, "代码块里的 < 被转义")

2.7 阅读时长公式：把假设写出来

weighted = 正文字符数 + 代码行数 * 20，再除以 400 字/分钟。
代码行按 3 秒折算成 20 字，这个系数是拍的——但它写在代码里，读者可以改。

这比"约 5 分钟"这种黑箱数字诚实：读者能算出你凭什么说 5 分钟，也能按自己的速度调整。

3.3 实验卡片字段

字段 来源 用途

3.4 发布前检查（人工部分）

体检器能查大部分机械项，最后一条得自己读：

  • 只有一个 H1，层级不跳
  • 代码块都有语言
  • 没有"显然/众所周知"，每个断言有出处
  • 每个数字带环境、样本量、重复次数、统计量
  • 至少一段命令能照着跑
  • 图片有 alt，没有遗留 TODO
  • 一个不在场的读者，能不能只靠文字复现你的结论

stable_output = len(hashes) == 1          # 结果可复现

翻车记录（真实踩坑）

翻车 1：自测报 W105 失败，我以为是规则坏了

  • 现象：--self-test 输出 ❌ W105 被检出，退出码 1。
  • 假设：图片 alt 检查的正则写错了。
  • 验证：把夹具打印出来看，图片那行是 ![图片](/x.png)——alt 不为空，规则本就该放过。
  • 根因：夹具写错了。我想测"缺失 alt"，却写了一个有 alt 的图片。
  • 修复：夹具改成 ![](/x.png)。
  • 复测：8 条全过，SELF-TEST PASS。

教训：自测失败时，先怀疑测试，再怀疑代码。这次如果直接改规则，会把一条正确规则改坏。

翻车 2：中文标题被 slug 成哈希，TOC 与 id 对不上

  • 现象：自测 ❌ 标题生成了与目录一致的锚点 id。
  • 假设：render_markdown 没用同一函数生成 href 和 id。
  • 验证：读代码确认两者都调 slugify()——一致，但输出是哈希 post-a15a2f6c。
  • 根因：slugify() 为文件名设计（ASCII 安全），纯中文标题折叠后只剩哈希；
    而 TOC 想显示原文，两者必然分叉。
  • 修复：拆出 anchor_id() 保留中文做锚点，slugify() 只管文件名。
  • 复测：id="为什么要写"，自测 14 条全过。

翻车 3：跨层引号把脚本改坏两次

  • 现象：SyntaxError: unterminated string literal；修完又出现
    closing parenthesis ']' does not match。
  • 假设：正则里的引号没转义。
  • 根因：改动同时穿过四层引用：shell heredoc → Python 字符串 → 正则 → 文件内容。
    每层都在吃引号，最终写进文件的代码少了一个反斜杠。
  • 修复：放弃内联字符串替换，改成"按行定位、整行重写"，并用 \x22 表示双引号。
  • 复测：自测 8/8，两篇文章体检全部通过。

教训：一次改动穿过三层以上引用时，不要拼字符串，直接重写整行/整块。

翻车 4：pkill -f 把自己的会话杀了

  • 现象：清理命令执行到一半，exec 返回 SIGTERM，后面的 ss 检查没跑。
  • 假设：服务进程没起来，pkill 空跑。
  • 验证：重新查端口，port free，说明服务确实停了；但没有"残留: 0"的输出，
    因为执行它的 shell 已经死了。
  • 根因：pkill -f '03-article-build.py' 的模式匹配到了执行这条命令的 shell
    自己的命令行    ，而命令行里就含这个字符串。
  • 修复：按端口判断（ss -ltnp | grep 8899）+ 按 PID 杀，不用模糊命令行匹配。
  • 复测：port free + no server process。

翻车 5：文章自称 168 行，实际 245 行

  • 现象：写完正文后 wc -l 一看，体检器是 245 行，不是正文里写的 168。
  • 根因：行数是边写边估的，中途加了 front matter 跳过、引号剥离、TODO 冒号规则，
    估的数字没跟着改。
  • 修复：发布前用 wc -l 校对，正文改成实测值（245 / 205 / 380，加上夹具 47 行）。
  • 教训：文章里每个数字都要有来源命令；这也是"可复现"的一部分——读者真的会数。

七、思考题

  1. 你的读者在什么场景下会关掉页面？如果只能保留文章的三段话，你保留哪三段？
  2. 体检器把"段落 > 400 字"设为警告。如果文章是 API 文档，这条规则还成立吗？该怎么改？
  3. 实验卡片记录 stdout 的 sha256。什么情况下"哈希不同"不代表实验失败？举两个例子。
  4. 为什么 noisy_timing 和 stable_output 必须分开判定？合成一个布尔值会丢什么信息？
  5. 你最近一次"我觉得这样更快"的判断，如果现在补一次 5 次重复的测量，最可能推翻什么？
  6. 静态站放弃了评论和搜索。如果你的文章主要靠讨论传播，这个取舍还合理吗？替代方案是什么？
