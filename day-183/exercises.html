Day 183 · 练习与检查表

目标：亲手跑通「构建镜像 → 起容器 → 一键部署 → 坏版本自动回滚 → CI 在本机跑绿」这条链， 并亲眼看见七个「绿着但没干活」的坑。 前置：Docker 可用；本机有 python3。全部命令都在 days/day-183-运维平台-容器化部署/ 下执行。

一、动手题（必做）

  • [ ] COPY --from=builder 搬的是什么？为什么不是搬整个 /build？
  • [ ] .dockerignore 里排掉了什么？如果漏掉 .env，后果是什么？
  • [ ] 自检里有一条 两者都不依赖 curl，为什么 Dockerfile 的注释里会出现 curl 这个词？（提示：翻车复盘第 1 条）
参考答案 `builder` 装了 gcc，`runtime` 没有。搬到 runtime 的只有 `/opt/venv`（依赖）与 `ops_service.py`； 不搬整个 `/build` 是因为那里还有 requirements.txt、字节码等构建期残留。 漏掉 `.env` → 密钥被打进镜像，而镜像会被推到仓库、被别的主机拉走。 注释里出现 curl 是因为注释在解释「为什么探针用 python3 而不是 curl」，断言必须先剥注释再判断。

docker image inspect day183-ops:single --format '{{.Size}}'; docker image inspect day183-ops:multi --format '{{.Size}}'
  • [ ] 两个变体的 inspect .Size 各是多少？差多少（MiB 和百分比）？
  • [ ] docker images 的 SIZE 列和 inspect .Size 差多少倍？你会在 README 里写哪个，怎么标注？
  • [ ] 多阶段的构建时间是更长还是更短？为什么值这个代价？
参考答案 本机实测：single 114,586,798 B（≈109.3 MiB）/ multi 47,352,410 B（≈45.2 MiB），省 64.1 MiB ≈ 58.7%。 `docker images` 列在**本机 legacy builder + overlayfs** 下比 `inspect .Size` 大约 4 倍 （434MB / 196MB）——**口径不同**，写文档要标清用哪个命令测的。 多阶段构建更慢（48.73s vs 40.67s），换来的是每个部署节点少拉 64 MB。

练习 4 — 起容器，看「健康」的两个时钟（10 分钟）

bash
docker run -d --name d183-ops -p 18080:8080 -e APP_VERSION=try1 day183-ops:multi
for i in $(seq 1 30); do curl -s -o /dev/null -w '%{http_code} ' localhost:18080/healthz; sleep 0.5; done; echo
docker inspect d183-ops --format '{{.State.Health.Status}}'
docker exec d183-ops sh -c 'command -v gcc || echo 没有 gcc'
  • [ ] curl 第几次拿到 200？.State.Health.Status 什么时候变成 healthy？
  • [ ] 两个时间差在哪？分别由 Dockerfile 里的哪几个参数决定？
  • [ ] 容器里有没有 gcc？这验证了多阶段的哪一点？
参考答案 本机实测：第 2 次探测（0.549s）就 200；HEALTHCHECK 到第 10 次（≈5s）才 `healthy`。 差值由 `--interval` / `--start-period` / `--retries` 决定：`start-period` 内的失败不计入 retries， 所以第一次判定点落在 `interval`。 没有 gcc → 构建期工具链确实没进运行镜像。

练习 5 — 一键部署 + 回滚演练（20 分钟，重点）

bash
python3 code/05-rollback-drill.py --dry-run
python3 code/05-rollback-drill.py
cat /tmp/day183/state/releases.json
  • [ ] 第二幕的 rc 是多少？它和「失败」是一回事吗？
  • [ ] 「判死耗时」和「回滚耗时」分别是多少？哪个是策略参数、哪个是性能？
  • [ ] releases.json 里 v2.0.0 出现在 current 了吗？为什么这个区别很重要？
  • [ ] 第三幕为什么必须存在？（提示：谁在自证）
参考答案 rc=2（**失败但已回滚**），与 rc=3（失败且无救）和 rc=0 都不同。 判死 ≈30.4s（= 健康检查超时，是**策略**）；回滚 ≈0.5s（是**性能**）。 v2.0.0 只在 `history` 且 `result: "failed"`，从不进 `current` —— 意味着它**从未接过流量**（先判后切 vs 先切后撤）。 第三幕用独立 curl 复核，因为**部署脚本的自述不能当证据**。

  • [ ] --dry-run 打出的拓扑序是什么？4 个 job 是并行还是串行？
  • [ ] 为什么 build / deploy 在 PR 上不跑？由哪一行控制？
  • [ ] --force-fallback 下哪几条断言被跳过？为什么是「跳过」而不是「失败」？

参考答案 顺序 `lint → test → build → deploy`（串行链，4 层）。 由 `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` 控制。 跳过的 3 条需要读深层结构（permissions.packages、matrix.fail-fast、steps 数量）， 正则后端解不出来——**标跳过是诚实，标通过是骗人**。 删掉 venv 会撞 PEP 668：`error: externally-managed-environment`，test job 两个腿全红（实测过）。

二、判断题（对/错 + 一句话理由）

  • [ ] docker run -d 返回 0 就说明服务已经可以接流量了。
  • [ ] EXPOSE 8080 会把端口发布到宿主机。
  • [ ] 多阶段构建之所以省空间，是因为 Docker 把中间层压缩合并了。
  • [ ] HEALTHCHECK 可以用 curl 写，因为 python:3.12-slim 里自带 curl。
  • [ ] 健康检查失败时，应该先把坏容器停掉再去收集日志。
  • [ ] 镜像标签用 latest 就够了，反正部署脚本会记下版本号。
  • [ ] CI 里某一步返回 0，就说明这一步真的干了它该干的事。
答案 1. ✗ 只是容器被创建了，进程可能还没绑定端口（本机实测 0.77s vs 0.549s 才可用）。 2. ✗ `EXPOSE` 只是声明；发布要靠 `-p`。 3. ✗ 没有合并——是**没搬**那些层过来。 4. ✗ slim 里没有 curl（本课实测踩过这个想当然），探针要用 `python3 -c`。 5. ✗ **先收日志**（`docker logs --tail`）再 `rm -f`，否则现场没了。 6. ✗ `latest` 是移动的靶子，回滚时无法精确指向；必须用 SHA。 7. ✗ 反例见翻车复盘第 10 条：`compileall` 对不存在的路径也返回 0。

三、排障演练

给三个现象，说出先查什么：

现象 你的第一步
docker run 成功，但 curl localhost:18080 一直连不上
镜像构建成功，但容器一启动就退出（Exited (1)）
部署脚本报「已回滚」，但用户说还是坏的
参考答案 1. 先 `docker ps -a` 看状态（是不是 `Exited`），再 `docker logs`； 若 Up 但连不上 → 看 `-p` 是否写对、服务是否绑 `0.0.0.0`（绑 `127.0.0.1` 时宿主访问不到）。 2. `docker logs ` 看退出原因；最常见是 `CMD` 里的路径/入口写错—— **构建期就该跑一次 `--once` 冒烟**（本课 Dockerfile 的 builder 阶段就是这么做的）。 3. 不信自述，独立复核：`curl /version` 看到底是哪个版本在服务； 再看 `releases.json` 的 `current`；最后确认回滚目标的健康检查**真的**通过过。
