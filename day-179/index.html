概念解释

Terraform 基础设施即代码（IaC）原理

Terraform 是实现基础设施即代码（IaC）的关键技术之一。IaC 意味着您可以声明云资源为机器可读的代码，而不是手工编写的配置脚本或 JSON 文件。

核心优势：
- 声明式：声明目标状态，而不是命令它
- 可读性：基础设施变为代码
- 版本控制：跟踪每次更改
- 可测试性：验证后自动应用

实施方式：
- 硬件转向 向代码 而不是手工
- 硬件 = 软件
- 硬件 = 软件

具体到云资源：
- 云提供商（AWS、GCP、Azure、阿里云等）
- 计算资源（EC2、GCE、虚拟机）
- 存储资源（S3、云硬盘、阿里云 OSS）
- 网络资源（VPC、子网、路由表）

云资源管理工具对比

传统方式 Terraform IaC
手动配置脚本 HCL 声明式
手工 JSON 配置 .tfstate 文件
手写文档 代码仓库
纸上谈 代码运行

对比优势：
- 一致性：每次执行声明后自动应用
- 状态追踪：完整版本控制系统
- 回滚能力：自动恢复到已知良好状态

Terraform 工作流 (Terraform Workflow)

1. Terraform 初始化 (Initialization)

bash
terraform init

初始化目的：
- 下载 Terraform 提供商插件
- 配置后端存储
- 创建 .terraform 目录

2. Terraform 计划 (Planning)

bash
terraform plan -out=tfplan

计划阶段：
- 读取 HCL 文件
- 查询云端状态
- 计算变更集合
- 生成执行计划

3. Terraform 执行 (Applying)

bash
terraform apply tfplan

执行阶段：
- 生成执行 ID
- 发送状态信号量
- 执行资源创建/更新/销毁
- 更新状态存储

4. Terraform 验证 (Validation)

bash
terraform validate

验证阶段：
- 语法检查
- 语义检查
- 类型检查

5. Terraform 销毁 (Destroying)

bash
terraform destroy -auto-approve

销毁阶段：
- 读取状态
- 执行销毁顺序
- 删除资源
- 更新状态

│    Init     │ →  │   Plan      │ →  │  Apply      │

    cidr_blocks = ["0.0.0.0/0"]
  }
  
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
  
  tags = {
    Name = "${var.environment}-ssh-sg"
  }
}

2. CI/CD 集成 (CI/CD Integration)

yaml
# GitHub Actions (GitHub Actions Workflow)
name: Terraform CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  TF_WORKING_DIRECTORY: ./infrastructure
  TF_REMOTE_BUCKET: "my-terraform-state"
  AWS_REGION: "us-west-2"

jobs:
  terraform-validate:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v3
      
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
        with:
          terraform_version: "1.5.0"
      
      - name: Terraform Init
        run: |
          cd $TF_WORKING_DIRECTORY
          terraform init -backend-config="bucket=${{ env.TF_REMOTE_BUCKET }}"
      
      - name: Terraform Validate
        run: |
          cd $TF_WORKING_DIRECTORY
          terraform validate
      
      - name: Terraform Plan
        run: |
          cd $TF_WORKING_DIRECTORY
          terraform plan -out=tfplan
        continue-on-error: false
  
  terraform-apply:
    needs: terraform-validate
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' || github.event_name == 'pull_request'
    steps:
      - name: Checkout
        uses: actions/checkout@v3
      
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v2
        with:
          terraform_version: "1.5.0"
      
      - name: Terraform Init
        run: |
          cd $TF_WORKING_DIRECTORY
          terraform init -backend-config="bucket=${{ env.TF_REMOTE_BUCKET }}"
      
      - name: Terraform Apply
        run: |
          cd $TF_WORKING_DIRECTORY
          terraform apply -auto-approve tfplan
        continue-on-error: false

Terraform 核心概念总结

1. Terraform 的核心特征

  • 声明式 (Declarative)：声明想要什么，而不是如何做
  • Idempotent：多次执行相同结果
  • 状态管理 (State Management)：跟踪基础设施状态
  • 插件架构 (Plugin Architecture)：支持多种云提供商

2. Terraform 主要组件

  • 配置 (Configuration)：HCL 文件
  • 提供商 (Provider)：云提供商接口
  • 资源 (Resource)：云端对象
  • 状态 (State)：基础设施状态存储
  • 后端 (Backend)：状态存储位置

3. Terraform 主要流程

  • 初始化 (Initialization)：下载插件，配置后端
  • 计划 (Planning)：分析变更，生成执行计划
  • 应用 (Applying)：执行变更，更新状态
  • 销毁 (Destroying)：销毁资源，更新状态

4. Terraform 主要概念

  • 资源 (Resource)：云端对象
  • 提供商 (Provider)：云提供商接口
  • 变量 (Variable)：配置参数
  • 输出 (Output)：重要信息的返回
  • 模块 (Module)：可重用组件
  • 状态 (State)：基础设施状态存储
  • 后端 (Backend)：状态存储位置

5. Terraform 主要文件类型

  • .tf 文件：HCL 配置文件
  • .tfvars 文件：变量文件
  • terraform.tfstate 文件：状态文件
  • .terraform 目录：Terraform 插件和缓存
  • .terraform.lock.hcl 文件：锁定文件

6. Terraform 的最佳实践

  • 文件组织 (File Organization)：合理组织配置文件
  • 变量管理 (Variable Management)：使用 .tfvars 文件
  • 输出定义 (Output Definition)：定义有用的输出
  • 模块化 (Modularity)：创建可重用模块
  • 版本控制 (Version Control)：使用 Terraform 的版本控制
  • 安全设置 (Security Settings)：配置适当的 IAM 策略

7. Terraform 的多云支持

  • AWS：hashicorp/aws 提供商
  • Google Cloud：hashicorp/google 提供商
  • Azure：hashicorp/azurerm 提供商
  • 多云部署：使用多个提供商定义资源

8. Terraform 的监控和合规

  • CloudWatch 监控 (CloudWatch Monitoring)：监控 Terraform 运行情况
  • 审计日志 (Audit Logs)：使用 CloudTrail 记录所有操作
  • 安全合规 (Security Compliance)：配置适当的 IAM 策略和日志记录
  • 成本监控 (Cost Monitoring)：监控基础设施成本

  6. 监控和合规性 (Monitoring and Compliance)：监控基础设施状态和确保合规性
  7. 版本控制 (Version Control)：使用版本控制管理基础设施

总结 (Summary)

Terraform 是一个强大的基础设施即代码工具，支持多云部署、自动化基础设施管理和安全合规。通过合理的配置和使用，可以显著提高开发效率和基础设施质量。

思考题

  1. 声明式与幂等：Terraform 的「声明式」和写脚本逐个调云 API 的「命令式」有什么区别？为什么同一份配置 terraform apply 两次不会创建两台机器？状态文件（.tfstate）在其中扮演什么角色？

参考答案

命令式描述「怎么做」：脚本一步步调 API 建 VPC、建子网、建实例。重复执行就会重复创建，你还得自己写「先查是否存在」的判断，出错后也很难回到一致状态。

声明式描述「要什么」：resource "aws_instance" "web" { instance_type = "t3.micro" } 只声明期望状态，由 Terraform 自己算出「现状 → 期望」的差集，只执行必要的动作。

幂等（idempotent，同一操作执行多次结果相同）正是差集为空的表现：第二次 apply 时，状态里已记录这台实例且属性完全一致，于是输出 0 to add, 0 to change, 0 to destroy，不会多出一台机器。

状态文件是「Terraform 眼中的现实」：记录每个资源的真实 ID、属性、依赖关系。配置里的 aws_instance.web 只是个逻辑名字，靠状态才能对应到云上某台具体机器，进而判断该更新、该替换还是什么都不做。所以实际有三份信息在比对：配置（期望）、状态（上次已知现实）、云端真实情况（refresh 后读到）。有人在控制台手改了资源，就会出现漂移（drift），plan 会把它显示出来。

⚠️ 注意：状态文件可能含敏感值（数据库密码、密钥），不要提交到 Git；团队协作要用远程后端（S3 / GCS / Azure Blob 等）并开启状态锁，防止两人同时 apply 互相覆盖。

  1. 工作流四步：terraform init、validate、plan、apply 各解决什么问题？为什么推荐 plan -out=tfplan 再 apply tfplan，而不是直接 apply -auto-approve？

参考答案

  • init：下载 provider 插件、初始化后端（状态存哪里）、生成 .terraform 目录和 .terraform.lock.hcl（锁定插件版本）。新增模块、换后端、升级 provider 后都要重新 init。
  • validate：只做本地检查——语法、类型、必填字段、引用是否存在。它不访问云端、不读状态，速度快，适合当 CI 的第一道关卡。
  • plan：读配置 + 读状态 + 查询云端（refresh），算出变更集合并以 + create / ~ update / - destroy 展示。这是预演，不动任何真实资源。
  • apply：真正执行变更，然后把结果写回状态。对应的 destroy 则按依赖逆序销毁状态中的资源。

plan -out=tfplan 把这次预演结果存成计划文件，apply tfplan 严格执行你审阅过的那一份。若直接 apply，Terraform 会重新计算计划——在你审阅之后、执行之前，配置或云端状态可能已经变了，于是「看的是一份计划、执行的是另一份」。CI 里的标准做法就是：PR 阶段产出 plan 供评审，合并后 apply 同一个计划文件。

-auto-approve 跳过交互确认，只适合自动化且计划已受控的场景；destroy -auto-approve 尤其危险，一条命令就能清空整套环境。

💡 提示：terraform plan -detailed-exitcode 的退出码可直接用于流水线判断——0 表示无变更、1 表示出错、2 表示有变更。

  1. 用 Python 模拟一次 plan（代码）：Terraform 的 plan 本质是「期望配置 vs 状态」的差集计算。请用标准库写一个迷你版，演示首次创建、重复执行无变更（幂等）、改配置后 update / destroy 三种情况，并说明它与真实 Terraform 的差距。

参考答案

python
# 依赖：仅标准库（纯本地模拟 plan 逻辑；真实 terraform 命令需自行安装并准备云账号）
import json

def plan(desired, state):
    """对比「期望配置」与「状态」，算出变更集合（简化版 terraform plan）"""
    actions = []
    for name, want in desired.items():
        have = state.get(name)
        if have is None:
            actions.append(("create", name, want))     # 状态里没有 → 新建
        elif have != want:
            actions.append(("update", name, want))     # 属性不同 → 更新
        else:
            actions.append(("no-op", name, want))      # 完全一致 → 什么都不做
    for name in state:
        if name not in desired:
            actions.append(("destroy", name, state[name]))   # 配置里删了 → 销毁
    return actions

def apply(actions, state):
    """执行变更并写回状态（简化版 terraform apply）"""
    for action, name, attrs in actions:
        if action == "destroy":
            state.pop(name, None)
        elif action != "no-op":
            state[name] = dict(attrs)
    return state

def show(actions):
    for action, name, _ in actions:
        print(f"{action:8s} {name}")
    changes = sum(1 for a, _, _ in actions if a != "no-op")
    print(f"Plan: {changes} to change")

# 期望状态：一台 web 实例 + 一个日志桶
desired = {
    "aws_instance.web": {"instance_type": "t3.micro", "tags": {"Env": "dev"}},
    "aws_s3_bucket.logs": {"bucket": "my-logs"},
}
state = {}                        # 第一次运行，状态文件还是空的

print("--- 第一次 plan ---")
actions = plan(desired, state)
show(actions)
state = apply(actions, state)     # apply 之后状态被写入

print("--- 第二次 plan（配置没改）---")
show(plan(desired, state))        # 全是 no-op，这就是幂等

print("--- 改配置后再 plan ---")
desired["aws_instance.web"]["instance_type"] = "t3.small"   # 升级机型
del desired["aws_s3_bucket.logs"]                           # 删掉一个资源
show(plan(desired, state))
print(json.dumps(state, ensure_ascii=False, sort_keys=True))

预期输出：

--- 第一次 plan ---
create   aws_instance.web
create   aws_s3_bucket.logs
Plan: 2 to change
--- 第二次 plan（配置没改）---
no-op    aws_instance.web
no-op    aws_s3_bucket.logs
Plan: 0 to change
--- 改配置后再 plan ---
update   aws_instance.web
destroy  aws_s3_bucket.logs
Plan: 2 to change
{"aws_instance.web": {"instance_type": "t3.micro", "tags": {"Env": "dev"}}, "aws_s3_bucket.logs": {"bucket": "my-logs"}}

desired 相当于 .tf 配置解析后的资源集合，state 相当于 terraform.tfstate。plan 就是逐资源比对生成动作列表，apply 就是执行这些动作并回写状态——第二次 Plan: 0 to change 直观展示了幂等：配置没变，现实就不该变。最后一行打印的是变更前的状态，说明 plan 阶段绝不修改状态，只有 apply 才会。

真实 Terraform 比这复杂得多：靠依赖图决定执行顺序（VPC → 子网 → 实例）；区分「就地更新」与「替换」（先 destroy 再 create）；用 count / for_each 展开多实例；data 数据源只读查询云端；还要做变量求值、模块展开，并由 provider 插件真正调用云 API。

⚠️ 注意：本例把机型变更简化成 update，真实 AWS provider 中不少字段变更会触发资源替换，plan 会标注 destroy and then create replacement——这意味着数据可能丢失，务必看清再 apply。本示例纯本地运行，不连云、不创建任何真实资源；要跑真 Terraform 需自行安装并准备账号凭证，练手建议先用 local / null provider。
